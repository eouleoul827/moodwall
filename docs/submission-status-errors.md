# 무드월 접수 상태와 오류 계약

기준일: 2026-11-05. [준비 완료 순서와 15초 재생 설계](playback-design.md)의 v2 경로에 [Gemini 검수](gemini-moderation-implementation.md)를 추가해 실행 코드와 OpenAPI 0.10.0에 반영했다. 실제 필드와 상태 값은 [HTTP 계약](openapi.json), 재생 사용법은 [로컬 연결 가이드](playback-local-implementation.md)를 따른다. 기존 [Problem 응답 구현](../backend/app/errors.py)의 형식·인증·입력 비반사 원칙을 재사용한다.

## Gemini 추가 계약의 상태

[Gemini 검수 설계](gemini-moderation-design.md)의 새 결정은 `ALLOW/BLOCK/UNCERTAIN`이다. 자기 감정·도움 요청만으로 새 SUPPORT를 만들지 않는다. 과거 사유 `SUPPORT_AVAILABLE`, 기능 헤더 `support-v1`, HTTP 409 `CLIENT_UPDATE_REQUIRED`는 기존 영수증 호환·원문 제거를 위해 유지한다. 해당 영수증은 `NEEDS_REWRITE`와 원문 purge 이전에 보존한 사유를 유지하되 학생에게 원문 미리보기나 도움 안내 없이 ‘이 글은 전광판에 표시되지 않았어요. 다른 내용으로 다시 작성할 수 있어요.’를 표시한다. 서버 전용 실제 HTTP 연결과 외부 호출 없는 mock을 구분하며 신고 API는 유지한다.

운영자 검수 상태의 `transportConfigured`는 서버 키 설정 여부이고, `workerReady`는 현재 bundle의 유효한 작업자 lease 여부다. 둘을 실제 모델 품질 검증으로 해석하지 않는다. `lastFailureCode`는 인증·한도·시간 초과 등의 고정된 코드만 반환하며 키·공급자 응답 본문·학생 원문은 포함하지 않는다. 연결 준비·복구·예산 부족 동안 새 접수는 기존 HTTP 503 `MODEL_NOT_READY`로 닫고, 진행 중 기술 실패는 제재 없이 종료한다. 이미 전송을 시작한 검수를 자동으로 다시 호출하지 않는다.

## 학생 화면의 기본 원칙

학생에게는 [학생 화면 최소 변경안](student-ux.md)에 따라 기존 완료 카드와 필요한 오류 안내만 보여준다. 접수를 확인하면 제목은 메시지를 보냈어요!로 통일한다. 분석·대기·재생 상태를 단계별로 노출하지 않는다. 아래의 상세 상태는 API·운영·중복 방지·복구를 위한 결과 구분이며 각각 새 화면을 만들라는 요구가 아니다.

## 서버가 성공을 판단하는 기준

서버에서는 요청을 DB에 안전하게 저장한 것, 준비를 마친 것, 전광판 앱이 표시를 시작한 것, 15초를 끝낸 것을 구분한다. 이 구분과 학생 화면을 단순하게 유지하는 것은 함께 적용한다.

| 결과 상태 | 서버 근거 | 학생 화면 원칙 | 서버의 완료 판단 |
| --- | --- | --- | --- |
| SENDING | 휴대폰이 접수 요청을 보내는 중 | 글을 보내고 있어요. | 미확정 |
| PREPARING | 접수 영수증·원문·예약·작업이 커밋됨 | 메시지를 보냈어요! 완료 카드 | 접수만 성공 |
| WAITING | 준비 완료 순번이 확정됨 | 같은 완료 카드 유지 | 아직 미표시 |
| STARTING | 서버가 시작을 승인했으나 첫 프레임 보고는 없음 | 같은 완료 카드 유지 | 아직 표시 확인 안 됨 |
| SHOWING | 현재 attempt의 첫 프레임 보고가 확정됨 | 같은 완료 카드 유지 | 아직 15초 완료 아님 |
| SHOWN | 유효한 완료 보고가 DB에 확정됨 | 같은 완료 카드 유지 | 정상 완료 |
| UNKNOWN | 통신 오류로 접수 결과를 모름. 클라이언트 전용 | 전송 결과를 확인하고 있어요. | 성공·실패 어느 쪽도 단정하지 않음 |
| PLAYBACK_UNCONFIRMED | 시작했을 수 있으나 정상 완료를 끝내 확인하지 못함 | 완료 카드 유지, 운영 복구 대상으로 처리 | 자동 새 글 전송 금지 |
| NEEDS_REWRITE | 필터 거절 또는 AI 비공개·불확실 판정 | 표현을 바꿔 다시 작성해 주세요. | 해당 글 종료 |
| FAILED | 준비 또는 복구가 기술적으로 실패함 | 준비 중 문제가 생겼어요. 잠시 후 다시 작성해 주세요. | 해당 글 종료 |
| EXPIRED | 게시 전 기한 또는 당일 표시 기한을 넘김 | 대기 시간이 지나 표시되지 않았어요. | 해당 글 종료 |
| CANCELLED | 시작 전 운영 취소 | 이 글의 표시가 취소됐어요. | 해당 글 종료 |
| HIDDEN | 운영자가 숨김 처리함 | 이 글은 전광판에서 내려갔어요. | 이후 표시 금지 |

SHOWN은 인증된 노트북 앱의 정상 완료 보고다. 실제 패널 전원·HDMI 출력까지 서버가 검증한 결과라는 표현은 쓰지 않는다. 원문 보관 상태는 별도 contentStatus = AVAILABLE 또는 PURGED로 반환한다. 원문을 지워도 userStatus·reasonCode·lastDisplayStatus·표시 시각·완료 시각을 유지한다. 즉시 원문을 삭제한 거절 결과도 계속 NEEDS_REWRITE로 안내하고, SHOWN 원문이 만료돼도 학생에게는 기존 완료 카드를 유지한다. 보관 종료 팝업을 추가하지 않는다.

## 접수와 조회 응답

POST /api/v2/submissions는 content만 받고 UUID Idempotency-Key를 요구한다. 동일 키는 동일한 사용자와 요청 계약 버전에 연결되며, 내용 수정 없이 재시도할 때 유지한다. 새 글을 명시적으로 작성할 때만 새 키를 만든다.

| 요청 | HTTP | 의미 |
| --- | --- | --- |
| 신규 접수 | 202 | 영수증·원문·수용량·작업의 원자적 커밋 완료 |
| 같은 키와 같은 내용 | 200 | 기존 접수 결과. 추가 글·작업·횟수 없음 |
| 본인 결과 조회 | 200 | 작업이 FAILED여도 결과를 정상적으로 읽었음 |
| 존재하지 않거나 다른 사람의 ID | 404 | 소유권 정보를 노출하지 않음 |
| 본인 영수증의 원문만 만료 | 200, contentStatus = PURGED | 본문 없이 원래 최종 결과·사유·시각 제공 |
| 영수증 24시간도 만료 | 404 | 멱등 보장 기간 종료, 자동 재접수하지 않음 |

응답 예시는 목표 DTO의 최소 필드다. usage·인증 헤더 등 기존 계약 요소도 구현 시 실제 OpenAPI에 함께 정의한다.

```json
{
  "receiptVersion": "2",
  "submissionId": "a820a8d5-97b9-4ad9-8892-91808957ca91",
  "acceptedAt": "2026-11-04T12:00:00+09:00",
  "receiptExpiresAt": "2026-11-05T12:00:00+09:00",
  "processingStatus": "PENDING",
  "presentationStatus": null,
  "userStatus": "PREPARING",
  "contentStatus": "AVAILABLE",
  "lastDisplayStatus": null,
  "reasonCode": null,
  "firstStartAuthorizedAt": null,
  "contentDeleteAt": null,
  "revision": "1",
  "statusUrl": "/api/v2/submissions/a820a8d5-97b9-4ad9-8892-91808957ca91",
  "message": "메시지를 보냈어요!"
}
```

GET /api/v2/submissions/{id}는 본인 세션만 확인한다. 이미 접수된 글의 조회에 새 QR·남은 작성 횟수·전광판 온라인 상태를 다시 요구하지 않는다. QR 입장권이 만료돼도 접수된 작업은 기존 기한 안에서 계속 처리한다. 세션을 잃어 다른 익명 사용자로 재입장한 경우에는 이전 영수증의 소유권을 자동 복구할 수 없다.

POST 응답을 잃어 submissionId를 모르면 POST /api/v2/submission-receipts/lookup에 원래 Idempotency-Key를 보내 본인 영수증을 찾는다. 이 조회용 POST도 Origin·CSRF·본인 세션을 검사하며 본문은 로그에 남기지 않는다. 키는 인증 토큰이 아니고 다른 사람의 영수증을 읽는 권한을 주지 않는다.

## 휴대폰의 전송과 결과 확인

1. 전송 전에 새 멱등 키와 정규화한 요청 내용을 고정한다. 화면의 중복 클릭을 막는 것과 서버의 중복 방지는 함께 적용한다.
2. 휴대폰에는 키·최초 전송 시각·알고 있는 submissionId만 24시간 이내로 보관한다. 재전송에 필요한 미확정 원문은 해당 작성 탭의 메모리 또는 만료가 있는 sessionStorage에 최대 10분만 보관하고, 접수 확인 즉시 지운다. 인증 토큰은 이 저장소에 넣지 않는다.
3. 202 또는 같은 키의 200을 받으면 기존 완료 카드로 이동한다. 화면이 열려 있는 동안만 PREPARING부터 뒤에서 조회한다. 준비 중에는 visible 상태에서 2초, WAITING에서는 5초 간격을 기본값으로 사용하고 중첩 요청은 하지 않는다. 숨김 탭에서는 주기를 멈추고 복귀 후 한 번 조회한다. 정상 상태 변경에 따라 카드 문구를 바꾸지 않는다.
4. timeout·브라우저 네트워크 오류·해석할 수 없는 게이트웨이 응답이면 UNKNOWN이다. 1·2·4·8·10초 간격과 작은 jitter로 영수증 조회를 재시도하고 Retry-After가 있으면 더 늦은 시각을 따른다. 5회 실패 후에는 자동 반복을 멈추고 같은 접수를 다시 확인하는 버튼을 제공한다.
5. lookup의 404만 보고 새 키를 만들지 않는다. 원래 요청의 커밋이 아직 끝나지 않았을 수 있다. 원래 내용을 보관 중이면 같은 키·같은 내용으로 POST를 다시 보낸다. 내용이 없으면 결과 재확인을 유지하며 다른 내용으로 자동 덮어쓰지 않는다.
6. SHOWN·수정 필요·확정 실패·만료·취소 등 terminal 결과면 반복 조회를 멈춘다. 명시적인 새 작성은 새 키를 쓰되 UNKNOWN을 실패로 간주해 새 글을 자동 전송하지 않는다.
7. 24시간이 지난 오래된 전송은 자동 재전송하지 않는다. 서버가 이미 지운 멱등 키를 영구히 기억한다고 약속하지 않는다.

모바일 재시도와 전광판의 start·complete 재시도는 별개다. 전광판 ACK가 실패했다고 학생이 글을 다시 보내게 만들지 않는다. 이전 요청의 늦은 응답은 인증 epoch·submissionId·revision을 비교해 현재 화면을 되돌리지 못하게 한다.

## 접수 전에 확정되는 오류

아래 오류가 앱의 정의된 Problem 응답으로 반환되면 해당 새 접수는 커밋하지 않는다. 이전의 같은 키 영수증이 존재하는 경우에는 새 접수 조건보다 기존 결과 반환을 먼저 수행한다.

| HTTP와 code | 상황 | 학생 안내와 처리 | 횟수·수용량 |
| --- | --- | --- | --- |
| 400 BAD_REQUEST | 손상된 JSON·요청 형식 | 요청을 다시 확인해 주세요. | 미차감 |
| 413 PAYLOAD_TOO_LARGE | 전체 요청 크기 초과 | 입력 길이를 확인해 주세요. | 미차감 |
| 415 UNSUPPORTED_MEDIA_TYPE | JSON이 아닌 본문 | 화면을 새로 열고 다시 시도해 주세요. | 미차감 |
| 422 VALIDATION_ERROR | 빈 글·30 grapheme 초과·제어문자·알 수 없는 필드 | 글은 1~30자로 작성해 주세요. | 미차감 |
| 401 SESSION_EXPIRED | 학생 세션 없음·만료·해지 | 접속을 다시 확인해 주세요. | 기존 접수 여부는 세션 복구 뒤 조회 |
| 403 ADMISSION_EXPIRED | 새 접수의 QR 권한 만료 | 전광판의 최신 QR을 다시 스캔해 주세요. | 미차감 |
| 403 PARTICIPANT_SUSPENDED | 당일 정지 | 오늘은 작성할 수 없어요. | 미차감, suspendedUntil 표시 |
| 403 CSRF_INVALID 또는 ORIGIN_FORBIDDEN | 요청 출처·CSRF 검사 실패 | 화면을 새로 열고 다시 시도해 주세요. | 미차감, 자동 우회 금지 |
| 409 SUBMISSION_IN_PROGRESS | 본인 글이 검수·준비 중 | 처리 중인 글을 먼저 확인해 주세요. | 기존 영수증으로 이동 |
| 409 IDEMPOTENCY_CONFLICT | 같은 키에 다른 내용·계약 버전 | 이전 전송 내용을 확인해 주세요. | 새 접수 없음 |
| 429 SUBMISSION_COOLDOWN | 접수 성공 뒤 10초 미경과 | 잠시 후 다시 작성해 주세요. | 미차감, Retry-After |
| 429 QUOTA_EXCEEDED | 최근 60분 3회 예약·소비 | 다음 작성 가능 시각을 확인해 주세요. | 미차감, nextSlotAt·Retry-After |
| 429 RATE_LIMITED | 요청 자체가 너무 잦음 | 잠시 후 다시 시도해 주세요. | 미차감, Retry-After |
| 503 INTAKE_PAUSED | 운영자가 접수 중단 | 지금은 글을 받고 있지 않아요. | 미차감 |
| 503 DISPLAY_OFFLINE | 유효한 전광판 소유자·lease 없음 | 전광판 연결을 확인하고 있어요. | 미차감 |
| 503 MODEL_NOT_READY | 검증된 모델이 준비되지 않음 | 분석 기능을 준비하고 있어요. | 미차감 |
| 503 MODERATION_BUSY | 처리 큐 상한·처리 기한 여유 부족 | 준비 중인 글이 많아요. 잠시 후 다시 시도해 주세요. | 미차감 |
| 503 DISPLAY_QUEUE_FULL | 전체 미완료 수용량 또는 예상 대기 초과 | 표시 대기가 많아요. 잠시 후 다시 시도해 주세요. | 미차감 |
| 503 DAY_ENDING | 당일 15초 재생을 마칠 여유 부족 | 오늘의 전광판 표시를 마감하고 있어요. | 미차감 |
| 503 SERVICE_UNAVAILABLE | DB·스키마·의존성 미준비로 커밋 전 확정 거절 | 잠시 후 다시 시도해 주세요. | 미차감 |

일반적인 500·502·503·504 응답은 위의 확정 거절과 다르다. 앱이 만든 유효한 오류 코드가 없거나 커밋 결과가 모호하면 UNKNOWN으로 복구한다. DB 커밋 확인에 실패한 서버도 새 키 재접수를 지시하지 않는다. 같은 키 재요청이 저장된 영수증을 확인하게 한다.

## 접수 후 작업의 실패

비동기 작업이 실패해도 결과 조회 HTTP는 200이다. userStatus와 reasonCode로 결과를 표현한다. 외부 AI·스토리지의 HTTP 코드나 예외 메시지를 그대로 학생에게 전달하지 않는다.

| 공개 reasonCode | 상태 | 처리·학생 안내 | 횟수와 제재 |
| --- | --- | --- | --- |
| CONTENT_REQUIRES_REWRITE | NEEDS_REWRITE | 표현을 바꿔 다시 작성하도록 안내 | 시작 전 예약 반환. 확정 규칙만 별도 위반 가산 |
| CONTENT_REVIEW_UNCERTAIN | NEEDS_REWRITE | 공개할 수 있는 내용으로 다시 작성하도록 안내 | 예약 반환, 위반 가산 없음 |
| CONTENT_REVIEW_UNAVAILABLE | FAILED | 제공자 안전 필터로 검수를 완료하지 못함. “내용 확인을 완료하지 못했어요. 이 글은 아직 전광판에 표시되지 않았어요. 다시 작성할 수 있어요.” | 예약 반환, 위반 가산·자동 재호출 없음 |
| PREPARATION_TIMEOUT | FAILED | 120초 준비 기한 초과, 늦은 결과 무시 | 시작 전 예약 반환, 제재 없음 |
| PREPARATION_UNAVAILABLE | FAILED | 모델·규칙 엔진·작업자·저장소 오류 | 시작 전 예약 반환, 제재 없음 |
| INVALID_ANALYSIS_RESULT | FAILED | 잘못된 라벨·NaN·스키마·정책 버전 불일치 | 시작 전 예약 반환, 제재 없음 |
| PRESENTATION_EXPIRED | EXPIRED | 최초 시작 전 10분 기한 초과 | 예약 반환, 제재 없음 |
| DAY_ENDED | EXPIRED | 당일 미표시 대기 종료 | 예약 반환, 제재 없음 |
| DISPLAY_CANCELLED | CANCELLED | 운영자가 시작 전 취소 | 예약 반환, 제재 없음 |
| DISPLAY_HIDDEN | HIDDEN | 운영자가 숨김, 이후 공급과 재생 차단 | 시작 전만 반환, 제재는 별도 근거 필요 |
| PLAYBACK_UNCONFIRMED | PLAYBACK_UNCONFIRMED | 허용한 복구 후에도 완료를 확인하지 못함 | 시작 후 자동 환불 없음, 운영 확인 가능 |

금칙어 일치 문자열·분해 결과·모델 점수·판단 프롬프트를 오류에 넣지 않는다. 확정 규칙 위반은 검수 단계에서 한 번만 가산하고 3회 경고·5회 당일 정지 안내를 별도 필드로 제공한다. AI 판정·서버 실패·배경 실패·대기 만료를 욕설 위반으로 세지 않는다.

원문 삭제는 contentStatus만 PURGED로 바꾼다. CONTENT_RETENTION_ENDED로 원래의 공개 reasonCode를 덮어쓰지 않는다. 영수증의 결과·사유와 원문 보관 여부는 독립적이다.

생성형 배경 실패나 노트북 자산 로딩 실패 뒤 기본 감정 테마로 정상 전환했다면 사용자 상태는 성공 경로를 유지한다. 내부 지표에는 fallback 사유를 남기되 학생에게 실패했다고 안내하지 않는다. 기본 테마도 사용할 수 없어 표시가 불가능할 때만 기술 실패다.

## 전광판 제어 오류와 복구

| HTTP와 code | 원인 | 노트북의 동작 |
| --- | --- | --- |
| 204 | claim할 READY가 없음 | 기존 말풍선 화면 유지, 다음 알림·조회 대기 |
| 401 DISPLAY_SESSION_EXPIRED | 장치 자격 없음 | 원문을 가리고 인증·페어링 복구 |
| 403 DISPLAY_REVOKED | 장치 해지·세대 교체 | 재생과 대기를 멈추고 캐시 정리 |
| 409 PLAYBACK_STALE | 이전 epoch·attempt·탭의 늦은 명령 | 새 재생을 변경하지 않고 현재 상태 조회 |
| 409 PLAYBACK_OWNED | 다른 유효한 탭·장치가 소유 중 | 중복 표시하지 않고 이전 lease 종료 대기 |
| 409 PLAYBACK_NOT_READY | 배경 준비 전·앞 글 활성·잘못된 전이 | 상태 재조회, 학생 재전송 금지 |
| 409 PLAYBACK_TOO_EARLY | 서버의 현재 시도 첫 프레임 보고 +15초 전에 complete | 정상 로컬 타이머를 확인하고 같은 명령으로 대기 후 재시도 |
| 409 START_AUTHORIZATION_EXPIRED | 고정 startNotAfter 이후 처음 도착한 frame 또는 늦게 사용한 시작 승인 | 새 글로 접수하지 않고 현재 항목의 중단 복구 절차로 전환 |
| 410 PRESENTATION_EXPIRED | 숨김·삭제 기한·미표시 기한으로 재생 불가 | 해당 본문·전체 화면을 제거하고 다음 유효 항목 조회 |
| 409 DISPLAY_VERSION_UNSUPPORTED | API·캐시·화면 계약 불일치 | 보호 화면과 업데이트 안내, 구버전으로 재생 금지 |
| 503 또는 네트워크 오류 | 상태 조회·명령 결과 불명 | 유효 lease 범위만 유지, 같은 명령 복구, 다음 글 임의 시작 금지 |

같은 start·frame·complete 명령이 이미 처리됐다면 정상 응답을 다시 준다. start 응답에는 원래의 startNotAfter를 유지하되 관측용 serverNow는 현재 DB 시각으로 갱신해 오래된 승인의 만료를 확인할 수 있게 한다. 완료된 시도의 지연된 중복 complete를 새 시도와 혼동해 재생을 다시 시작하지 않는다. 실제로 다른 시도를 변경하려는 오래된 요청만 PLAYBACK_STALE로 거절한다. 명령 영수증은 부모 제출 영수증의 수명 안에서 보관한다. TOO_EARLY 같은 일시적인 무변경 거절은 최종 결과로 캐시하지 않아 대기 후 같은 키로 성공할 수 있게 한다.

완료 ACK가 없다고 일정 시간 뒤 SHOWN으로 바꾸지 않는다. 새로고침으로 로컬 타이머를 잃었을 때는 서버 재생 상태·남은 명령·원문 기한·장치 소유권을 먼저 맞춘다. 이 복구에서 학생의 새 제출 요청을 만들지 않는다.

## 오류 응답과 운영 확인

Problem 응답은 application/problem+json, X-Request-ID, Cache-Control: no-store를 사용한다. 일시 제한에는 Retry-After를 준다. 사용자 문구는 공개 오류 코드별 고정 문구를 사용하고 내부 예외 내용을 넣지 않는다. 모바일과 전광판은 HTTP status만 보고 재시도하지 않고 code와 자원의 상태를 함께 해석한다.

학생 화면의 상태 확인은 읽기 실패와 작업 실패를 구분한다. 조회 API의 일시적인 503이면 이전 완료 카드를 실패로 바꾸거나 매번 알림을 추가하지 않는다. 복구 후 더 큰 revision의 결과를 반영하되, 학생이 조치할 수 있는 확정된 거절·게시 전 실패만 짧게 안내한다. requestId·접수 ID는 지원용 정보로만 두고 정상 완료 카드에 기술 정보를 나열하지 않는다. 운영자는 원문 없이 큐·상태·시각·작업 버전을 확인한다.

## 수락 시나리오

| 시나리오 | 기대 결과 |
| --- | --- |
| 전송 버튼 연타 | 같은 키는 영수증·작업·횟수 하나 |
| 원문 저장 후 큐 등록 실패 | 전체 롤백, 성공 화면 없음 |
| 커밋 성공 후 응답 단절 | UNKNOWN → 같은 키 조회·재전송 → 기존 접수 확인 |
| 두 학생이 마지막 수용량을 동시에 요청 | 하나만 성공, 다른 요청은 미차감 거절 |
| 준비 중 QR 교체·입장권 만료 | 기존 작업과 본인 조회는 계속, 신규 작성에는 새 QR 요구 |
| 느린 A와 빠른 B 준비 | B가 먼저 READY가 되면 B부터 표시 |
| 현재 글 재생 중 새 READY 도착 | 현재 글은 정상 15초를 채움 |
| 이미지 생성 실패 | 기본 테마 성공이면 WAITING·SHOWN 경로 유지 |
| AI가 invalid 결과 반환 | 공개하지 않고 FAILED, 위반 가산 없음 |
| 확정 규칙 결과 callback 중복 | 위반 횟수 한 번만 가산 |
| first frame 보고 유실 | SHOWING·SHOWN으로 추정 확정하지 않고 같은 attempt 복구 |
| 15초 재생 후 complete 응답 유실 | 동일 complete 응답 복구, 새 제출·만료 연장 없음 |
| lease 만료 뒤 옛 complete 도착 | 새 재생에 영향 없음, 명령 이력에 따른 멱등 결과 또는 STALE |
| 준비 기한·대기 기한 초과 | 늦은 승인·배경 결과가 글을 되살리지 않음 |
| 표시 전 만료 후 다시 같은 키 전송 | EXPIRED 영수증 반환, 새 글 생성 없음 |
| 원문 삭제 후 본인 조회 | contentStatus = PURGED와 원래 최종 결과·사유·완료 시각, 본문 없음 |
| 빠른 거절 직후 원문 삭제 | 다음 조회에도 NEEDS_REWRITE와 원래 사유 유지 |
| 영수증 만료 뒤 오래된 탭 복귀 | 자동 재전송 없음, 새 작성은 명시적인 행동으로만 |
| 다른 사람의 접수 ID로 조회 | 없는 ID와 같은 404, 원문·상태 유출 없음 |

정상 경로·DB 경쟁·작업 종료·브라우저 복구를 각각 검증한다. API 단위 시험만으로 실제 휴대폰·전광판·HDMI의 성공을 선언하지 않는다. 이 문서의 신규 코드는 목표 OpenAPI·백엔드 오류 매핑·프론트 상태 관리·통합 시험이 함께 구현될 때 완료로 본다.

## 공식 기준

- 202는 처리 완료를 뜻하지 않는다는 구분은 [RFC 9110의 202 Accepted](https://www.rfc-editor.org/rfc/rfc9110.html#name-202-accepted)를 따른다. 이 앱에서는 별도 영수증 조회로 진행 결과를 제공한다.
- 오류 본문의 표준 구조는 [RFC 9457 Problem Details](https://www.rfc-editor.org/rfc/rfc9457.html)를 따른다. code·requestId·재시도 메타데이터는 앱의 확장 필드다.
- 앱·캐시 버전 불일치는 409와 공개 코드로 표현한다. [426 Upgrade Required](https://www.rfc-editor.org/rfc/rfc9110.html#name-426-upgrade-required)는 연결 프로토콜 전환에 관한 상태이므로 이 용도로 사용하지 않는다.
