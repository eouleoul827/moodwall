# 데이터·동시성·장애 복구 설계

현재 DB head는 `0006_playback_receipts`다. 새 [v2 로컬 구현](playback-local-implementation.md)과 [15초 재생 설계](playback-design.md)는 영수증 분리·READY 순번·재생 시도·최초 시작 승인 기준 만료를 사용한다. [schema.sql](schema.sql)도 0006을 포함한다. 아래 기존 제출 중심·접수 후 1시간 설명은 v1 호환 경로에 적용하며, v2 원문 삭제 후에도 본문 없는 영수증을 접수 후 24시간 유지한다.

상태: 구현 전 기준안 · 검토일: 2026-10-29 · 대상: 학교 1곳·전광판 1대

이 문서는 [`schema.sql`](schema.sql)의 의미와 서비스가 지켜야 할 규칙을 정한다. SQL은 새 PostgreSQL 16+ DB에 적용할 기준 DDL이며 실행 완료된 애플리케이션이나 운영 마이그레이션은 아니다. Procrastinate 자체 테이블은 고정한 라이브러리 버전의 마이그레이션으로 생성한다. 별도 Redis·Supabase 서비스는 전제하지 않는다.

## 1. 저장소 선택과 신뢰 경계

PostgreSQL을 멘션·작성 제한·검수 작업·화면 상태의 원본으로 쓴다. API와 검수 작업자는 서로 다른 프로세스로 실행한다. 프론트는 DB에 직접 접속하지 않는다. SSE는 상태 변경을 알리고, 재연결 시 REST로 현재 상태를 다시 받는다.

API·작업자 DB 계정은 DDL 소유자·슈퍼유저가 아니다. 애플리케이션 SQL은 매개변수 바인딩을 사용하고, DB 포트는 사설 네트워크로 제한한다. 운영 마이그레이션은 별도 계정으로 순차 실행한다. 백업 복구 환경을 제외한 운영 데이터에 개발자의 개인 도구를 직접 연결하지 않는다.

| 테이블 | 책임·주의점 |
|---|---|
| `participants` | 익명 참여자와 마지막 새 제출 시각. 실제 학생·기기 식별 증거가 아니다. |
| `browser_sessions` | 무작위 세션 토큰의 SHA-256 해시와 QR 입장 허가 만료. 클라이언트가 참여자 ID를 정하지 않는다. |
| `daily_usage` | `(participant_id, business_date)`별 위반 수와 당일 정지 기한만 관리. 작성 쿼터는 저장하지 않는다. |
| `submissions` | 접수·검수·표시 이력. 최근 60분 쿼터는 이 상태를 조회해 계산한다. |
| `board_runtime` | 화면 모드·일시정지·상태 버전·heartbeat·전광판 장치 자격. |
| `operators`, `operator_sessions` | 개인별 운영자 계정과 별도 세션. 학생 세션과 권한을 섞지 않는다. |
| `operator_audit_logs` | 숨김·정지 해제 등 운영 변경의 행위자·시각·사유 코드. 원문·토큰은 기록하지 않는다. |
| `rate_limit_buckets` | 선택적인 공유 요청 속도 제한. 원시 IP를 장기 식별자로 저장하지 않는다. |
| `worker_readiness` | 검증된 모델·작업자 준비 상태를 감독 프로세스가 5초마다 갱신하는 15초 임대. |

한 장치만 등록하므로 `board_runtime`에 활성 장치 해시 하나를 둔다. 장치를 추가로 운영한다면 해당 시점에 `display_devices`로 분리한다. 학생·운영자·장치 토큰은 각각 독립적인 256-bit 난수이며 원문을 DB에 보관하지 않는다. 비밀번호는 단순 SHA-256이 아니라 Argon2id 등 비밀번호 전용 해시를 사용한다. CSRF 토큰은 세션 쿠키와 권한 범위에 바인딩한 서버 HMAC으로 파생하며 DB 필드를 추가하지 않는다.

## 2. 시간·정책

- DB에 시점은 `timestamptz`로 저장한다. 업무 날짜는 서버가 `Asia/Seoul`로 계산한다.
- `accepted_at`은 서버 시각이며 클라이언트가 보내지 않는다. `business_date`도 이 시점의 한국 날짜다.
- 접수 기한은 `min(accepted_at + 120초, 다음 한국 자정)`이다. DB 제약도 상한을 검증한다.
- 트랜잭션을 기다린 뒤 만료·정지를 검사할 때는 오래된 요청 시각이나 트랜잭션 시작 시각을 재사용하지 않는다. 잠금 획득 후 `clock_timestamp()`로 확인한다. `now()`는 트랜잭션 시작 시각으로 고정되므로 이 검사에 쓰지 않는다. [DB 시각 함수](https://www.postgresql.org/docs/16/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT)
- QR은 5분마다 교체하고 현재·직전 QR을 각각 전체 구간 동안 인정한다. 발급 시각부터 10분인 `ticket.validUntil`을 입장 허가 만료로 저장한다. 만료 직전 스캔도 새로 10분을 주지 않는다. 새 유효 QR을 스캔할 때만 허가를 갱신한다. 같은 전광판에서 최신 QR을 이미 교환했다면 늦게 도착한 직전 QR 요청으로 만료를 앞당기지 않도록 기존 만료와 새 `validUntil` 중 큰 값을 유지한다.
- 30일 세션은 참여자 식별용이며 QR 작성 허가와 다르다. QR이 자정을 넘으면 허가도 고정 만료까지 유지된다. 허가가 만료되면 새 접수에는 QR 재스캔이 필요하지만 기존 제출 상태 조회는 가능하다.
- 익명 참여자 기준 **rolling 최근 60분에 최대 3회**다. 정각이나 한국 자정에 초기화하지 않는다. 서버 접수 시각이 최근 60분 안이고 검수 상태가 `PENDING`·`PROCESSING`·`APPROVED`이면 쿼터를 소비한다. 승인 후 숨기거나 화면에서 만료해도 접수 60분까지는 소비 상태다.
- 참여자당 검수 중 1개, 새로운 접수 사이 10초를 적용한다. 자정을 넘어도 10초 간격은 유지한다.
- 검증된 금칙 규칙만 위반 수를 올린다. 3회 경고, 5회 한국 자정까지 정지다. 모델 불확실·시스템 오류는 제재하지 않는다.

VM과 DB의 시각 동기화도 운영에서 확인한다. 참여자 잠금 뒤 `quota_now < last_submission_at`이면 DB 시각이 뒤로 이동한 것으로 보고 새 접수만 일시 실패시킨다. 미래로 보이는 이전 접수를 rolling 창에서 빼고 새 접수를 받아서는 안 된다. 브라우저는 서버 시각과 monotonic 경과를 사용해 시계 역행으로 투명 전환·자정 판정이 뒤로 밀리지 않게 한다. 큰 시각 점프가 감지되면 접수를 잠시 중지하고 동기화를 복구한다. 실행 감시의 경과 시간은 DB wall clock을 반복해서 빼지 않고 부모의 monotonic 시계로 측정한다.

검수 중 요청은 상태 자체로 쿼터를 예약하므로 `reserved_count`·`approved_count`·`reservation_held` 같은 중복 집계를 두지 않는다. DB CHECK만으로 여러 제출의 최근 60분 합계를 제한할 수 없으므로, 쿼터에 영향을 주는 모든 변경을 **참여자 행 잠금**으로 직렬화한다. [PostgreSQL CHECK의 범위](https://www.postgresql.org/docs/current/ddl-constraints.html)

학교 Wi-Fi·LTE·5G를 모두 허용하고 학교망 IP 허용 목록은 적용하지 않는다. 학교 밖에서 유효한 QR을 공유받으면 입장할 수 있다. 요청의 `Origin`은 웹사이트 출처이며 학생의 물리적 위치나 학교 네트워크를 증명하지 않는다. IP는 보조 트래픽 보호에만 사용하고 개인별 횟수·제재 키로 사용하지 않는다. QR 만료는 짧은 작성 허가의 종료이며 현장 체류의 증명이 아니다.

## 3. 멱등성: 다시 보낸 요청은 다시 차감하지 않는다

프론트는 의도적인 새 제출마다 UUID `Idempotency-Key`를 만든다. 응답이 끊기거나 재시도할 때는 같은 키와 같은 본문을 사용한다. 내용 수정·명시적인 새 제출에는 새 키를 쓴다.

정규 JSON을 SHA-256으로 해시한다. 고정 계약 버전 `v1`·서버가 승인한 NFC 표시 문장·`emojiId`를 포함하고 객체 순서를 고정한다. 처리 결과에 영향을 주는 모든 요청 필드는 포함하되 모델·정책 버전은 포함하지 않는다. 처리 중 정책이 바뀌었다고 같은 의도가 새 요청이 되면 안 되기 때문이다. 초기 버전의 정규화 순서·해시 대상·고정 버전은 배포마다 바꾸지 않는다. 향후 이를 바꾸려면 명시적인 새 요청 계약과 버전 저장 방법을 추가하고 기존 보관 기간의 재전송을 계속 지원해야 한다. 이 해시는 인증 수단이 아니며 원문과 함께 외부로 공개하지 않는다.

1. 유효한 학생 세션으로 참여자를 복원하고 요청 크기·구조와 동결된 v1 문장 정규화를 검증한다. 현재 emoji 활성 목록처럼 배포에 따라 바뀌는 신규 접수 정책은 아직 검사하지 않는다.
2. 기존 `(participant_id, idempotency_key)`를 찾는다. 같은 해시면 현재 결과 반환, 다른 해시면 `409 IDEMPOTENCY_CONFLICT`다.
3. 기존 요청이 없을 때만 현재 emoji ID의 신규 사용 가능 여부·입장 허가·정지·최근 60분 쿼터·새 제출 간격을 검사한다. 과거 제출의 emoji가 비활성화되어도 기존 키 재조회는 그 이유로 막지 않는다.
4. 신규 접수 트랜잭션에서 같은 키를 다시 조회한다. 사전 조회 뒤 다른 요청이 먼저 접수되었을 수 있다.
5. DB UNIQUE 위반은 트랜잭션 전체를 롤백한 뒤 기존 기록을 재조회하여 처리한다. 새 제출이나 작업만 남기지 않는다.

유효한 세션 소유자의 기존 요청 조회는 짧은 QR 입장 허가 만료·이후 정지·쿨다운 때문에 막지 않는다. 세션 자체가 만료되거나 취소되면 소유자 검증이 안 되므로 결과를 공개하지 않는다. 실패·만료된 요청의 동일 키 재전송도 기존 실패·만료 결과를 돌려준다.

멱등 응답 보장은 원본 접수 후 1시간 보관 기간 안이다. 삭제된 키를 따로 기억하는 tombstone은 두지 않는다. 1시간 뒤 같은 키가 오면 새 접수로 해석될 수 있으므로 프론트는 오래된 실패 요청을 자동 재전송하지 않는다. 만료된 상태 조회는 404이며 원문과 결과를 복구하지 않는다. 정상 검수 기한은 최대 120초이므로 그 안에서 같은 키를 재조회·재전송하고, 만료 뒤의 새 작성은 사용자가 명시적으로 시작한 새 키만 사용한다.

## 4. 잠금 규칙

기본 격리 수준은 `READ COMMITTED`다. 행 잠금·조건부 갱신·UNIQUE를 조합하며 전 트랜잭션을 SERIALIZABLE로 바꾸는 것으로 정확성을 대체하지 않는다. [PostgreSQL 격리 설명](https://www.postgresql.org/docs/current/transaction-iso.html)

| 동작 | 잠금 순서 |
|---|---|
| 새로운 접수 | `participants` → 해당 날짜 `daily_usage` → 기존/새 `submissions` |
| 검수 시작·최종화·기한 만료·정지 | `participants` → 원래 날짜 `daily_usage` → `submissions` |
| 화면 배정·모드 변경·숨김·heartbeat·장치 교체 | `board_runtime` → `submissions` |
| 페어링 코드 발급 | 해당 `board_runtime`만 |

최종화 작업도 참여자부터 잠근다. 어떤 경로도 제출을 먼저 잠그고 참여자를 뒤늦게 잠그지 않는다. 화면 작업은 `participants`·`daily_usage`를 잠그지 않으며 검수 상태를 바꾸지 않는다. 같은 영역의 두 개 이상 제출을 잠글 때는 불변 UUID 정렬 순서를 사용한다. 하나의 트랜잭션에서 제재·쿼터 영역과 전광판 영역을 함께 갱신하지 않는다. 운영자 숨김과 제재 복구도 필요하면 별도 작업으로 나눈다.

기한 정리의 배치 조회는 잠금 없는 후보 조회로 제한하고 후보 한 건마다 별도 트랜잭션을 연다. `submissions FOR UPDATE SKIP LOCKED`로 먼저 잡아 놓고 참여자를 잠그는 구현은 금지한다. 먼저 참여자를 잠근 뒤 해당 제출의 현재 상태·기한을 재확인한다. 잠긴 건을 건너뛰어야 한다면 첫 참여자 잠금에 `NOWAIT`를 적용하고 그 건 전체를 다음 주기로 넘긴다. 전광판 작업도 먼저 전광판 행을 잠근 후 대상 제출 ID를 모아 정렬 잠금한다. PostgreSQL은 일관된 잠금 순서를 교착 예방 수단으로 제시하며, `SKIP LOCKED` 결과는 완전한 업무 상태 조회가 아니다. [잠금 순서](https://www.postgresql.org/docs/16/explicit-locking.html#LOCKING-DEADLOCKS), [SKIP LOCKED 범위](https://www.postgresql.org/docs/16/sql-select.html#SQL-FOR-UPDATE-SHARE)

행 잠금 상태에서 모델 호출·네트워크 호출·SSE 전송을 하지 않는다. 잠금 시간 초과·교착·연결 실패 시 전체 트랜잭션을 롤백하고 한정된 지수 지연으로 재시도한다. 재시도에도 같은 멱등 키를 쓴다. API가 DB를 오래 점유하지 않도록 `lock_timeout`, `statement_timeout`, `idle_in_transaction_session_timeout`을 설정한다.

## 5. 신규 접수 트랜잭션

부분 UNIQUE는 기한을 자동 판단하지 않는다. 미정리 `PENDING` 행이 새 접수를 가로막지 않도록, 사전 단계에서 소유자의 기한 초과 제출이 보이면 **별도 만료 트랜잭션**으로 정리하고 신규 접수를 재시도한다. 만료 작업은 참여자 → 원래 날짜 제재 집계 → 제출 순으로 잠그며 실제 DB 기한을 재검사한다. 이는 정상 정리 작업의 지연을 보완한다. 두 단계 사이 다른 접수가 생기면 부분 UNIQUE와 재검사로 검수 중 1개를 유지한다.

```text
BEGIN
  참여자 행 FOR UPDATE
  같은 멱등 키 재조회 → 기존이면 새 접수 없이 반환
  DB 시각의 한국 날짜로 오늘 제재 집계 INSERT ... ON CONFLICT DO NOTHING
  해당 날짜 제재 집계 FOR UPDATE
  quota_now = 잠금 획득 뒤 clock_timestamp()
  quota_now의 한국 날짜가 잠근 날짜와 다르면 ROLLBACK 후 처음부터 재시도
  quota_now가 last_submission_at보다 이전이면 새 접수 일시 실패
  quota_now 기준으로 QR 허가 만료·당일 정지·10초 간격 검사
  처리 중 제출이 있으면 409 SUBMISSION_IN_PROGRESS
  최근 60분 PENDING/PROCESSING/APPROVED 제출 수 < 3 검사
  검수 준비 상태·접수 중단 설정·미검수 backlog soft gate 검사
  submission(PENDING) INSERT → 상태 자체가 쿼터 예약
  같은 psycopg 연결에서 Procrastinate 작업 INSERT
  queue_job_id와 participant.last_submission_at 기록
COMMIT
202 + submissionId
```

당일 제재 집계는 UPSERT 뒤 잠근다. 자정 경합으로 날짜가 달라지면 롤백하고 새 날짜로 재시도한다. 전역 혼잡 상한은 미검수 PENDING/PROCESSING 작업을 위한 접수 제어 soft gate다. 승인된 글의 표시 대기열은 없으며 화면 자리 부족으로 접수를 거절하지 않는다. 구체 값은 [운영 기준](delivery-and-operations.md)을 따른다. 서로 다른 참여자의 동시 관측은 cap을 넘을 수 있으므로 실제 모델 처리량·대기 시간 경보와 함께 운영한다.

검수 작업 등록이 실패하면 제출을 포함한 전체 트랜잭션을 롤백한다. 예약은 별도 카운터가 아니라 제출 상태에서 유도되므로 미커밋 요청의 횟수는 소비되지 않는다. 다른 연결로 작업을 등록하고 나중에 커밋하는 방식은 금지한다. Procrastinate는 공식적으로 `psycopg.Connection` 및 `psycopg.AsyncConnection`을 넘겨 같은 트랜잭션에서 작업을 등록할 수 있다. 버전을 고정하고 시작·롤백 통합 테스트로 확인한다. [외부 연결 문서](https://procrastinate.readthedocs.io/en/stable/howto/production/external_connection.html)

쿼터 조회는 참여자 잠금을 획득한 후 DB 시각 `quota_now`를 한 번 읽어 다음 조건을 사용한다. 신규 행의 `accepted_at`과 참여자의 `last_submission_at`도 이 시각으로 명시적으로 설정하고, 업무 날짜·처리 기한을 이 시각에서 계산한다. 제재 날짜와 달리 rolling 조회에는 `business_date` 조건을 넣지 않는다.

```sql
SELECT count(*)
FROM submissions
WHERE participant_id = $1
  AND accepted_at > $2::timestamptz - interval '60 minutes'
  AND accepted_at <= $2::timestamptz
  AND moderation_status IN ('PENDING', 'PROCESSING', 'APPROVED');
```

예를 들어 10:00·10:10·10:20의 승인된 접수가 있으면 11:00에 첫 건이 창에서 빠진다. 10:00 접수가 10:01에 승인되어도 만료는 승인 60분 뒤가 아니라 접수 60분 뒤인 11:00이다. 쿼터 초과의 재시도 시각은 가장 오래된 소비 접수의 `accepted_at+60분`으로 계산하되, 검수 결과에 따라 더 일찍 반환될 수 있다.

## 6. 검수 작업의 시작·재시도·확정

검수 상태:

```text
PENDING → PROCESSING → APPROVED / REJECTED / NEEDS_REWRITE / FAILED / EXPIRED / CANCELLED
           └─ 검증된 일시 오류 재시도 → PENDING
```

시작 트랜잭션은 참여자 → 원래 날짜 제재 집계 → 제출 순으로 잠근다. 제출이 최종 상태면 작업은 끝낸다. 이미 유효한 다른 실행이 `PROCESSING` 중이면 중복 작업을 실행하지 않는다. DB 현재 시각이 전체 기한 이상이면 `EXPIRED`, 시도 수가 2이면 `FAILED`로 끝내고 세 번째 실행을 시작하지 않는다. 실행을 받으면 새 UUID `processing_run_token`, `processing_started_at`, 임대 기한을 저장하고 `attempt_count`를 증가시킨 뒤 커밋한다. 영속 작업 인자는 `submission_id`만 둔다. 원문·세션·IP를 큐 인자와 작업 로그에 복제하지 않는다.

모델 실행은 트랜잭션 밖이다. 실행 임대는 `min(processing_started_at + 60초, expires_at)`으로 고정하고, START/ACK 대기·추론·결과 확정에 이 예산을 함께 사용한다. heartbeat·START 지연·재시도가 이번 임대를 연장하지 않는다. 부모는 DB가 정한 남은 예산을 monotonic 타이머로 감시한다. 임대가 끝난 실행은 같은 token으로 다시 살아나지 않는다. 모델 실행 후 결과를 잃거나 임대가 만료되면 `FAILED`(`WORKER_LOST` 또는 `INFERENCE_TIMEOUT`)로 끝내고 재추론하지 않는다. 전체 기한도 끝났다면 `EXPIRED`가 우선이다. 짧은 서비스에서 중복 CPU 실행 회수 프로토콜을 추가하기보다 해당 요청을 안전하게 종료하고 새 요청을 받을 수 있게 하는 초기 운영 선택이다.

최종화 트랜잭션은 참여자 → 원래 날짜 제재 집계 → 제출 순으로 잠그고 다음을 모두 검사한다.

- 상태가 `PROCESSING`이다.
- 실행 token이 현재 DB token과 같다.
- 모든 행 잠금 획득 뒤 읽은 DB 현재 시각이 `processing_lease_until`과 `expires_at` 모두 이전이고 원래 업무 날짜 안이다.
- 참여자가 정지되지 않았다.

같은 token이라도 60초 임대를 넘긴 결과로 승인·위반 집계를 하지 않는다. 전체 기한이 남아 있으면 `FAILED/INFERENCE_TIMEOUT`, 전체 기한이 끝났으면 `EXPIRED`로 종료한다. 이미 다른 token이나 최종 상태라면 아무 변경 없이 버린다. 이 검사와 최종 상태 UPDATE를 같은 트랜잭션 안에서 수행한다. 최종화의 기준 시각은 모든 잠금 획득 직후 한 번 읽은 값이며, 모델 계산을 마친 시각을 클라이언트나 자식 프로세스가 주장해 대체하지 않는다.

내부 최종화 입력은 [AI 계약](ai-contract.md)의 `RuleRejected | ModelAnalyzed | RunFailed`다. 확정 규칙 거절을 `AnalysisResult`로 꾸미지 않는다. `RuleRejected`는 `REJECTED`, `strike_applied=true`, 비어 있지 않은 `rule_evidence`를 같은 트랜잭션에 기록한다. 이 경우 모델을 호출하지 않았으므로 `model_bundle_version`, `inference_policy_version`, `safety_verdict`, `emotion`, `emotion_source`는 NULL, AI `reason_codes`는 빈 배열이다. 모델 결과는 `rule_evidence=[]`이며 AI BLOCK·UNCERTAIN을 `REJECTED`로 바꾸지 않는다.

`rule_evidence`는 최대 5개의 `{rule_id, variant_id}` JSON 객체다. 각 ID는 `[A-Za-z0-9_.-]`의 1~100자로 제한하고 다른 키·원문·검색 뷰·오프셋을 허용하지 않는다. 최종화가 활성 CONFIRMED 매칭을 `(rule_id, variant_id)` 순으로 정렬·중복 제거한 뒤 처음 5개만 보존한다. 버전은 제출의 `lexicon_version`에서 복원한다. DB의 순수 IMMUTABLE 검증 함수와 CHECK가 배열·객체 형태 및 REJECTED 전용을 검증한다. 운영자 응답에는 `ruleId`, `variantId`로 매핑하고 학생·전광판 응답에는 넣지 않는다. 매칭이 여러 개여도 제출당 위반은 한 번이다.

| 결과 | 제출 상태 | 사용량 변경 |
|---|---|---|
| 정상 공개 | `APPROVED`, 표시 `FLOATING` | 최근 60분 소비 유지 |
| 확정 금칙 규칙 | `REJECTED` | 쿼터에서 제외, 원래 날짜 위반 +1 |
| 모델 차단·불확실 | `NEEDS_REWRITE` | 쿼터에서 제외 |
| 복구 불가 오류 | `FAILED` | 쿼터에서 제외 |
| 기한·날짜 초과 | `EXPIRED` | 쿼터에서 제외 |
| 이미 정지·운영 취소 | `CANCELLED` | 쿼터에서 제외 |

최종화 시 실행 token·임대 필드는 NULL, `finalized_at`은 DB 시각으로 바꾼다. 상태 변경과 위반 집계 변경은 하나의 트랜잭션이다. 이미 최종 상태면 아무 제재도 다시 반영하지 않는다. 승인 후 화면 만료·숨김·감정 재검토가 `APPROVED`를 바꾸지는 않으며, 원래 접수 60분까지 소비가 유지된다.

5회 위반 시 참여자 → 해당 날짜 제재 집계를 잠근 상태에서 정지 기한을 다음 한국 자정으로 설정하고, 그 참여자의 같은 날짜 모든 `PENDING/PROCESSING` 제출을 정렬해 잠가 `CANCELLED`로 바꾸며 쿼터에서 제외한다. 현재 정책의 검수 중 1개 제한 때문에 일반적으로 다른 작업은 없지만 방어적으로 처리한다. 이미 승인된 글은 자동 삭제하지 않는다.

운영자의 당일 제한 복구는 참여자 → 제재 집계 잠금 안에서 `violation_count=0`, `banned_until=NULL`로 바꾸고 같은 트랜잭션에 이전·이후 값과 사유를 감사 기록으로 남긴다. 최근 60분 쿼터나 과거 접수 시각을 초기화하지 않는다. 과거 제출의 `REJECTED`와 `strike_applied=true`는 그대로 두고 다시 공개하지 않는다. 따라서 현재 위반 수를 역사상 모든 strike 합계와 같다고 가정해서는 안 된다.

제재 복구에는 운영자가 생성한 UUID `Idempotency-Key`를 필수로 받는다. 감사 기록의 `command_key`, SHA-256 `request_hash`와 초기화가 함께 커밋된다. hash는 고정 계약 버전·action·대상 participant ID·원래 businessDate·reasonCode의 정규 표현에서 만든다. `(operator_id, action, command_key)`의 기존 감사 기록을 날짜·대상 신규 검증보다 먼저 찾고, 같은 hash면 **초기화를 다시 하지 않고** `auditId`, `replayed=true`, 원래 `businessDate`와 DB 현재 한국 날짜의 `usage`를 반환한다. 다른 hash면 `409 IDEMPOTENCY_CONFLICT`다. 응답 유실 뒤 새 위반이 생겨도 같은 키의 재전송이 그 위반을 지우지 않는다. audit ID와 원래 날짜는 명령의 영수증이고, usage는 과거 응답 복제가 아니라 현재 값이다.

기존 명령이 없을 때만 참여자 → 해당 날짜 제재 집계를 잠그고 같은 키를 재조회한 뒤, 잠금 후 DB 날짜가 요청 날짜와 같은지 확인하여 초기화와 감사 기록을 저장한다. 두 대상에 같은 키가 동시에 들어가면 감사 UNIQUE 위반 시 **초기화까지 전체 롤백**한 뒤 별도 트랜잭션으로 기존 명령을 조회한다. `RESET_RESTRICTION`에만 키·32바이트 hash가 필수이며 다른 감사 action에는 둘 다 NULL이다. 멱등 보장은 감사 보관과 같은 90일이며, 만료 후 자동 재전송하지 않는다. 과거 명령의 재조회는 자정 후에도 가능하지만 새 복구 명령은 당일에만 허용한다. 30일 정리로 대상 참여자가 사라진 경우 기존 명령이 있어도 현재 usage를 가상 생성하지 않고 404를 반환하며 재초기화하지 않는다. 현재 상태는 운영자의 참여자 usage 조회로 다시 확인할 수 있다.

자동 재시도는 모델 실행을 시작하기 전의 허용한 일시적 의존성 오류에만 적용하며 총 실행은 초기 최대 2회다. 실패한 시도의 상태를 `PROCESSING → PENDING`으로 바꾸고 token·시작·임대 필드를 비우는 변경도 참여자 잠금 안에서 한다. 이미 모델을 시작한 뒤의 timeout·작업자 유실·잘못된 출력·판정 결과는 재추론하지 않는다. 기한이 끝났거나 남은 실행 예산이 없으면 재시도하지 않는다. DB 최종화 응답만 끊긴 경우에는 모델을 다시 실행하지 않고 동일 token·저장 결과의 최종화 또는 이미 저장된 terminal 결과 조회만 재시도한다. 자세한 결과 계약은 [`ai-contract.md`](ai-contract.md)를 따른다.

claim 시 접수의 `moderation_policy_version`, `lexicon_version`을 현재 배포의 고정 manifest와 비교한다. 일치하지 않으면 추론·제재 없이 `FAILED/POLICY_VERSION_MISMATCH`로 끝낸다. API의 기대 model bundle, 유효 readiness의 bundle, 실제 로드 artifact도 같아야 한다. `ClaimedRun`은 실행 token과 함께 로드 manifest의 model·inference 버전을 고정하고, 최종화는 `AnalysisResult`가 주장한 두 버전이 그 값과 같은지 검증한다. 결과의 문자열만 믿고 실행 이력을 기록하지 않는다. 모델·사전·정책을 실행 중 hot reload하지 않는다. 배포 전에는 접수를 멈춘 후 기존 `PENDING`와 `PROCESSING` 모두를 이전 bundle로 완료하거나 정해진 기한·취소 절차로 terminal화하고, 구 작업자 종료를 확인한 뒤 새 bundle을 시작한다. 이미 승인된 글을 새 모델로 자동 재판정하지 않는다.

## 7. 멈춘 작업 복구는 두 가지 문제다

**DB 안전성:** API 측 독립 정리 루프가 5초마다 전체 기한 초과 제출과 실행 임대가 끝난 `PROCESSING`을 작은 배치로 찾는다. 참여자 → 원래 날짜 제재 집계 → 제출 잠금 뒤 DB 시각으로 다시 검사하여 전체 기한 초과는 `EXPIRED`, 그보다 먼저 실행 임대만 끝나면 `FAILED/INFERENCE_TIMEOUT`으로 끝내고 쿼터에서 제외한다. 배치 대상 조회와 최종 잠금을 분리하여 조회한 상태가 여전히 맞는지 다시 확인한다. 작업자가 멈춰도 이 루프는 실행되어야 한다. 단순 readiness lease 만료만으로 아직 유효한 제출 실행을 실패 처리하지 않는다.

**CPU·메모리 회수:** async 취소와 DB 기한 만료는 native 모델 실행을 멈추지 않는다. AI 계약의 외부 감시 부모가 작업 시작 ACK·실행 예산·종료를 관리하고, 기한 초과 시 TERM 후 5초 뒤 KILL·reap하여 작업자 컨테이너를 실패 종료한다. 컨테이너 재시작 정책이 새 작업자를 시작하고 모델 준비 상태를 다시 확인한다. API 프로세스는 함께 종료하지 않는다.

Procrastinate 작업자가 강제 종료되면 `doing` 작업이 남을 수 있으므로, 독립 관리 루프가 약 10초마다 `get_stalled_jobs(seconds_since_heartbeat=30)`로 확인한다. 라이브러리 heartbeat 갱신은 초기 10초이며 관련 worker timeout 설정과 함께 고정 버전에서 검증한다. 실행 시간만 보는 `nb_seconds` 탐지는 쓰지 않는다. heartbeat 소실은 프로세스가 실제 종료됐다는 증거가 아니므로, 아직 유효한 `PROCESSING`의 모델을 재실행하지 않는다. 임대·전체 기한에 따른 업무 terminal 처리를 먼저 끝낸 후, terminal 상태임을 확인한 stalled job만 지원되는 `retry_job`으로 다시 전달한다. 그 task는 terminal 제출을 읽고 모델을 호출하지 않은 채 정상 반환하여 큐 기록만 종료한다. 제출이 없는 오래된 작업도 같은 no-op 경로다. 라이브러리의 기본 예제 10분 주기를 서비스 복구 목표로 오해하지 않는다. [중단 작업 복구 문서](https://procrastinate.readthedocs.io/en/stable/howto/production/retry_stalled_jobs.html)

큐 상태 변경 API와 업무 상태 잠금을 한 트랜잭션에 섞어 라이브러리 내부 잠금 순서를 추정하지 않는다. 위 관리 루프는 **업무 terminal화 커밋 → 라이브러리 API 호출** 순서로 분리한다. 두 번째 단계가 실패해도 다음 점검에서 재시도할 수 있고 쿼터는 이미 해제되어 있다. 라이브러리 내부 테이블을 임의 UPDATE하여 `doing`을 지우지 않는다.

수락 기준은 “프로세스가 다시 켜졌다”가 아니라 **정상 제출 하나가 다음으로 처리되고, 쿼터 누수·중복 승인·중복 위반이 없는 것**이다. 감시 부모·컨테이너 재시작·stalled 회수는 구현 후 강제 종료 테스트를 통과해야 하며 문서만으로 검증되었다고 간주하지 않는다.

### 모델 준비 상태 임대

작업자가 실행 중이라는 사실과 검증된 모델이 준비되었다는 사실을 구분한다. 감시 부모는 모델 해시 검사·로드·warmup·READY ACK를 확인한 뒤 `worker_readiness`에 고정 worker 이름·새 generation UUID·모델 bundle 버전·DB 시각을 기록한다. 5초마다 `WHERE generation=현재generation`인 조건부 UPDATE로 15초 임대를 갱신한다. 초기 행이 없거나 임대가 끝났거나 배포가 요구한 bundle 버전과 다르면 새 접수는 `503`이다.

작업자가 멈췄는데 부모만 살아 있다고 무기한 ready를 갱신하지 않는다. START/DONE·실행 예산·자식 생존을 관찰하고 hard timeout·비정상 종료 시 갱신을 멈추며 `DELETE WHERE worker_name=... AND generation=현재generation`으로 해당 임대를 즉시 없앤다. 재시작은 새 generation을 발급하므로 구 프로세스의 늦은 조건부 갱신·삭제가 새 상태를 덮지 못한다. 초기 배포는 supervisor 1개와 작업자 1개를 유지하며 **구 작업자 종료 확인 → 새 작업자 시작** 순서로 교체한다. 새 generation 최초 등록을 경쟁하는 rolling update는 지원하지 않는다. 준비 상태 갱신은 자체 행만 건드리고 전광판 상태나 참여자 쿼터를 수정하지 않는다. 모델 준비 완료 전에는 Procrastinate 작업 소비를 시작하지 않는다.

Procrastinate 자체 heartbeat는 중단 작업 탐지에 사용하며 모델 readiness를 대신하지 않는다. API가 확인한 직후 작업자가 죽는 경합은 완전히 없앨 수 없으므로 이미 접수된 건은 기한 만료·쿼터 반환으로 복구한다. 이 준비 상태·임대 흐름도 실제 중단 테스트의 대상이다.

## 8. 전광판 말풍선과 페이지 동기화

```text
서버: NONE → FLOATING → EXPIRED → 접수 1시간 뒤 행 삭제
                    └→ HIDDEN
로컬: 받은 FLOATING → expiresAt에 내용 담긴 AMBIENT → ambientUntil 자정 정리
```

검수 최종화는 전광판 행을 잠그지 않고 APPROVED·FLOATING을 저장한다. 승인 즉시 공개 원문 조회 대상이 되며 4개 자리 제한·강조·표시 대기열은 없다. 조정 루프는 약 2초마다 전광판 → 제출 순서로 기한 초과·전날 FLOATING만 작은 배치로 EXPIRED 처리한다. 조회는 정리 지연과 무관하게 업무 날짜·접수 1시간 미만을 검사한다.

전광판 페이지는 `(finalized_at,id)` 오름차순 keyset 정렬이며 한 번에 100개다. `submissions_floating_order_idx`는 board·업무 날짜·확정 시각·ID를 인덱싱하고 accepted_at을 INCLUDE한다. 첫 페이지의 `snapshotAt`까지 승인된 글만 포함해 끝까지 읽으며, 100개는 전송 단위이므로 전체 승인 글 4개·100개 제한을 뜻하지 않는다. 매 poll은 cursor 없는 첫 페이지부터 다시 시작한다.

서명 커서는 전광판·기기 세대·업무 날짜·첫 snapshotAt·마지막 정렬 키·5분 만료를 묶는다. 각 페이지에서 장치 인증·현재 업무 날짜·숨김·TTL을 다시 확인한다. 오류·변조·다른 scope·만료는 422 INVALID_CURSOR로 처리하며 프론트는 첫 페이지부터 다시 동기화한다. 페이지별 짧은 REPEATABLE READ READ ONLY는 그 응답 내 일관성만 제공하고 여러 HTTP 요청의 동일 MVCC snapshot을 보장하지 않는다. 페이지 사이 숨김·만료·삭제로 개수가 줄어들 수 있다. `revision`·`serverNow`는 최신 값으로 증가할 수 있다.

mode는 MOODWALL|CHATBOT과 운영자 display_paused를 분리한다. PAUSED·CHATBOT·heartbeat lease 만료는 화면을 가리는 조건이며 승인·목록 수집·DB 보관 시각을 늘리거나 별도 잔여 시간을 만들지 않는다. heartbeat는 10초 주기로 보내고 lease는 마지막 확인부터 30초다. 장치 명령은 전광판 행 잠금 뒤 token hash·version·만료를 다시 검사한다.

카드 `acceptedAt`은 접수 시각, `expiresAt=acceptedAt+1시간`은 DB/API 원문 공급 종료, `ambientUntil`은 다음 KST 자정이다. 프론트는 승인 글을 당일 캐시에 합치고 expiresAt부터 같은 글의 투명 말풍선으로 유지한다. 목록의 ID 부재·서버 EXPIRED·물리 DELETE는 캐시 삭제 신호가 아니다. 자정에는 이전 날짜 캐시를 비우고 조회의 오늘 날짜 필터가 전날 글을 막는다.

숨김은 전광판 → 제출 잠금 순서로 HIDDEN과 감사를 저장한다. 제출 행이 이미 삭제되어도 오늘의 원문 없는 숨김 감사를 남겨 로컬 말풍선을 지운다. 같은 전광판·날짜·ID 숨김은 멱등하다. `removedIds`는 최근 당일 숨김 최대1000개, `cacheResetToken`은 잘린 경계 감사ID이며 토큰 변경 시 오래된 캐시를 비운다. 기기 세대 변경도 캐시 초기화 경계다. SSE는 원문 없이 새 동기화를 알리고, 연결·재연결·10초 주기 조회로 복구한다. 숨김과 캐시의 세부 규칙은 [HTTP 계약](backend-contracts.md)을 따른다.

## 9. 장치 교체·운영자 변경

운영자가 만든 페어링 코드는 무작위 일회용이며 해시와 5분 만료만 저장한다. 등록은 전광판 행 잠금 안에서 코드를 검증·소비하고 장치 token hash·만료·세대를 교체하며 이전 heartbeat·lease를 비운다. 기존 장치 쿠키는 즉시 무효다. 응답 유실은 `GET /api/display/session`으로 현재 쿠키부터 확인하고, 유효 쿠키가 없을 때 새 코드를 발급한다. 소비한 pairing code로 쿠키를 복구하지 않는다.

학생 브라우저 쿠키의 초기 만료는 30일(절대), 전광판 장치는 마지막 사용 후 180일(사용 중 하루 한 번 연장, [보안 문서](security-and-operations.md)), 운영자는 보안 문서의 짧은 만료 정책을 따른다. 매 API 요청에서 DB 만료·회수 상태를 확인하므로 오래된 클라이언트 쿠키 자체를 신뢰하지 않는다. 운영자 비밀번호 변경·비활성화 시 관련 세션을 회수한다. 운영자별 계정을 사용하고 마지막 ADMIN은 CLI 복구 절차 없이 비활성화하지 않는다.

기존 학생 세션의 입장 허가를 갱신하거나 세션을 정리할 때도 먼저 해당 참여자를 잠그고, 세션 행의 현재 token·만료·회수를 다시 검사한다. 새 접수는 참여자 잠금 뒤 현재 세션의 입장 허가를 재검사한다. 장치 heartbeat·mode 변경은 `board_runtime FOR UPDATE`를 얻은 뒤 현재 장치 hash·version·만료를 다시 검사하고 정산·갱신한다. 인증 후 잠금 대기 중 해지·재페어링된 옛 요청이 새 장치의 lease나 mode를 덮어쓰면 안 된다.

운영자는 절대 만료 8시간과 마지막 유효 활동 후 30분 유휴 만료를 적용한다. `operator_sessions.last_seen_at`은 만료를 확인한 뒤 성공한 권한 POST에서만 갱신하며 GET·자동 polling은 연장하지 않는다. 갱신 때문에 `expires_at`을 늘리지 않는다. ADMIN은 기기 페어링·회수·송출 모드·접수 중단·감사 조회·운영자 관리를 담당한다. ADMIN과 MODERATOR 모두 멘션 목록 조회·숨김·당일 제한 복구를 할 수 있다. 실제 요청마다 보안 문서의 권한 표를 적용한다.

## 10. 정리·보관·백업

원문·검수 결과·멱등 응답을 담는 제출 행은 서버 접수 후 1시간에 삭제한다. 승인·차단·숨김 모두 동일하다. 전광판 브라우저가 이미 받은 공개 원문은 당일 로컬 저장소에서 다음 KST 자정까지 유지한다. 자정에 실행 중이 아니었다면 다음 시작 때 이전 날짜를 지우고 인증·상태 동기화 전에는 표시하지 않는다. 서버 DB 삭제만으로 이 사본까지 삭제됐다고 설명하지 않는다. 운영 DB를 재학습 데이터로 자동 반출하지 않는다. 학생 세션 30일, 일일 제재 집계 30일, 원문 없는 운영자 감사 90일은 제출 원문 수명과 별개다. 로그·백업·교육용 추출도 별도 정책이 필요하다.

| 주기 | 처리 |
|---|---|
| 약 2초 | 화면 조정·오늘 표시 상태 변경 |
| 약 5초 | 기한 초과 예약 반환, 작업자 준비 상태·최근 결과 점검 |
| 약 10초 | stalled worker 검사와 terminal 작업의 조건부 no-op 회수 |
| 약 5초 | 접수 1시간이 된 terminal 제출을 최대 100건씩 삭제. 비최종 상태는 먼저 기한 만료 처리 |
| 매시간 | 30일 이전이고 참조 제출 없는 daily_usage 삭제, 만료 세션 삭제, 참조 없는 오래된 익명 참여자 삭제 |
| 매시간 | 만료 rate-limit bucket·페어링 코드 정리, 감사 기록 정책 적용 |
| 매일 | Procrastinate 지원 API로 오래된 완료 작업만 정리. payload는 제출 ID만 포함 |
| 매일·배포 전 | 백업 상태 확인, 변경 전 복구 지점 확인 |
| 정기 | 격리 환경에서 백업 복원·앱 상태 조회 검증 |

원문 삭제는 완료 작업 정리를 기다리지 않는다. `queue_job_id`는 라이브러리 테이블의 FK가 아닌 양수 UNIQUE 핸들이므로 두 정리 주기가 독립적이다. 제출 삭제 → 참조 없는 사용량 → 만료 세션 → 참조 없는 참여자 순으로 참조를 지키며 정리한다. Procrastinate 지원 API로 종료 작업만 정리하고, `doing`·대기 작업을 원문 정리라는 이유로 직접 삭제하지 않는다. 제출이 사라진 작업은 재전달돼도 원문을 복원하거나 모델을 실행하지 않고 끝난다. [완료 작업 정리 문서](https://procrastinate.readthedocs.io/en/stable/howto/production/delete_finished_jobs.html)

현재 업무 날짜의 제재 집계는 삭제하지 않는다. 접수 1시간이 지난 terminal 제출과 오래된 제재 집계는 참여자별 별도 트랜잭션에서 참여자 → 날짜 순 집계 → ID 순 제출 순서로 삭제하며 현재 참조·보관 기한을 재검사한다. 1시간 삭제 경계는 최근 60분 쿼터가 빠지는 경계와 같아 사용량을 일찍 반환하지 않는다. 세션 정리와 참조 없는 참여자 삭제도 참여자부터 잠그고 세션·제출·제재 집계 참조가 없을 때만 수행한다. 한 번에 최대 100건의 후보를 조회하되 여러 참여자를 하나의 큰 트랜잭션에 잠그지 않는다. 만료되었어도 참조가 남은 부모 행은 `ON DELETE RESTRICT`가 삭제를 거부하도록 두고 강제 cascade로 우회하지 않는다. 참여자·업무 날짜·접수 시각은 생성 후 변경하지 않는다.

운영자·전광판은 소프트 비활성화하며 감사 로그의 외래키를 깨는 강제 삭제를 하지 않는다. `operator_audit_logs.target_id`는 제출·참여자 삭제 후에도 사건이 남도록 의도적으로 FK가 없고, 표시할 때 대상이 없음을 허용한다. 원문이 없는 감사 기록은 초기 90일 보관을 기본으로 하고 운영 정책이 확정되면 조정한다. 접수 1시간이 지나도 여전히 `PENDING`인 행은 먼저 검수 기한 만료·일치성 점검 후 정리한다. 정리 루프는 정상 상태에서 약 5초마다 실행하지만 잠금·DB 장애·쌓인 배치 때문에 DELETE가 늦어질 수 있어 지연을 감시한다. 조회 제외는 이 지연과 무관하게 1시간 경계를 지킨다.

원문을 1시간에 SQL DELETE해도 백업·WAL·디스크의 옛 바이트가 즉시 덮어써지는 것은 아니다. 초기 백업 보관 목표는 7일이며 삭제 전 생성된 사본에는 그 백업의 만료까지 원문이 남을 수 있음을 운영 정책에 적는다. 복원 환경은 외부 접근을 막고 최신 만료·정리 작업을 실행한 다음 운영에 노출한다. 외부로 이미 표시·내보낸 내용까지 DB 삭제가 회수하지는 않는다.

초기 백업 목표는 최소 일일 백업(RPO 최대 24시간), 복구 목표 RTO 4시간이다. 이는 테스트할 목표이지 관리형 DB를 고른 것만으로 보장되는 수치가 아니다. 행사 중 하루치 제재·글 유실을 허용할 수 없다면 PITR과 실제 복원 테스트를 출시 조건으로 올린다. 클라우드 장애와 전광판 노트북 장애를 구분해 점검한다.

격리 복원은 접수·송출을 중단하고 운영자 세션·장치 자격·pairing·readiness·heartbeat·lease·학생 QR 입장 허가를 폐기한다. 학생 식별 세션은 원래 만료를 지키되 새 QR이 필요하다. 구 작업자의 접근 차단과 오래된 비최종 업무 정리 후 새 supervisor·장치·smoke를 검증하고 재개한다. [운영 기준](delivery-and-operations.md)을 따른다.

DB 풀은 초기 API 최대 5·검수 작업자 최대 3·관리 작업 최대 2 연결 정도에서 측정 후 조정한다. 마이그레이션·백업·운영 연결 여유도 남긴다. SSE 연결마다 DB 연결 하나를 계속 점유하지 않고 짧은 쿼리 시에만 풀을 빌린다.

## 11. 일치성 점검과 검증 조건

다음 조회는 현재 rolling 창의 운영 진단용이다. 결과가 있으면 해당 참여자 접수를 멈춘 뒤 기록과 작업 상태를 대조한다. 중복 카운터를 복구할 필요는 없지만, 승인된 제출을 단순히 `FAILED`로 고쳐 쿼터를 되돌리는 식의 임의 수정은 하지 않는다.

```sql
WITH audit_clock AS (SELECT clock_timestamp() AS checked_at)
SELECT s.participant_id, count(*) AS consumed
FROM submissions AS s CROSS JOIN audit_clock AS a
WHERE s.accepted_at > a.checked_at - interval '60 minutes'
  AND s.accepted_at <= a.checked_at
  AND s.moderation_status IN ('PENDING', 'PROCESSING', 'APPROVED')
GROUP BY s.participant_id
HAVING count(*) > 3;
```

최소 통합 테스트:

1. 최초 제재 집계 행이 없는 참여자의 동시 접수에서 검수 중 1개·최근 60분 소비 3개 이하를 유지한다.
2. 동일 키·동일 본문 재전송이 하나의 제출·예약·작업을 만들고 다른 본문은 409다.
3. 기존 키 재조회는 QR·입장 허가 만료나 이후 정지에도 소유 세션이 유효하면 가능하다.
4. 작업 등록 직전·직후 강제 종료에서 세 데이터가 함께 커밋되거나 함께 취소된다.
5. 승인 직후 작업자 종료·중복 작업·늦은 token 결과에도 승인·위반·예약이 한 번만 반영된다.
6. 5회 정지와 정상 결과가 경합할 때 잠금 순서대로 확정되고 뒤늦은 공개가 없다.
7. 자정 직전 접수·자정 뒤 결과·새날 접수에서 원래 날짜 제재를 정리하고 rolling 쿼터는 자정에 초기화하지 않는다. 예를 들어 23:50의 승인은 다음날 00:50까지 소비한다.
8. 모델 무한 대기 fixture에서 실제 프로세스가 종료·회수되고 다음 정상 작업이 처리된다.
9. mode·오프라인·복구·숨김에도 별도 강조·표시 대기가 생기지 않고 원문 1시간·로컬 자정 수명과 숨김이 유지된다.
10. 백업 복원 후 제출·사용량·장치 인증·작업 복구와 원문 정리 정책을 검증한다.
11. 전체 120초 기한은 남았어도 실행 임대가 끝난 결과는 승인·위반을 반영하지 않는다. 기한 경계 직전 최종화가 행 잠금을 기다리면 획득 후 DB 시각으로 실패 처리한다.
12. 자정 직전 제재 집계를 선택한 접수가 잠금 대기 후 새날로 넘어가면 전체 롤백 후 재시도하여 날짜·accepted_at·기한이 일치한다.
13. stalled 회수는 업무 terminal 상태를 먼저 저장하고 task를 no-op로 종료한다. old 프로세스의 늦은 결과·동일 job 재전달·정리 루프 중단에도 재추론·중복 제재가 없다.
14. 정리와 최종화·운영자 숨김이 겹쳐도 정해진 잠금 순서를 유지하고, 감사 기록은 대상 삭제 후 조회되며 1시간 안의 멱등 응답은 완료 큐 작업 삭제에 영향받지 않는다. 정확히 1시간이면 공개·본인·운영자 조회에서 제외하고 제출 행을 삭제한다. 중단·오프라인·대기도 연장하지 않는다.
15. 복구 응답 유실 → 새 위반 → 동일 키 재전송에서 새 위반을 보존하고 같은 audit ID·현재 usage를 반환한다. 같은 키·다른 대상 동시 복구는 UNIQUE 경합의 패자 초기화도 롤백한다. 자정 후 재전송은 기존 명령만 조회한다.
16. 규칙 거절은 모델 호출 0회·한 번의 위반·최대 5개의 정렬된 근거를 기록하고 가짜 모델 필드는 남기지 않는다. 근거의 스칼라·누락 키·추가 키·과대 ID·6개 배열과 비거절 상태의 근거를 DB가 거부한다.
17. 배포 전 미처리 PENDING가 남아 있으면 교체 gate가 실패한다. 잘못된 bundle claim·결과 버전 불일치는 게시·제재 없이 종료하고, 이전 실행의 늦은 결과도 무시한다.

DDL의 음성 사례도 별도로 확인한다. 세 번째 attempt, attempt 0인 `PROCESSING`, 접수보다 앞선 실행 시작 시각, 60초를 넘긴 실행 임대, 전체 기한 이후 승인, 접수보다 앞선 확정 시각, 중복 `queue_job_id`는 DB가 거절해야 한다. `processing_lease_until`은 확정 시 지우므로 실제 최종화 시각이 임대 안인지의 검사는 DB CHECK가 아니라 최종화 트랜잭션의 책임이다. 이 음성 사례만으로 동시성이나 작업 회수를 검증했다고 보고하지 않는다.

앱과 작업자의 실제 통합 테스트는 아직 실행하지 않았다. 임시 PostgreSQL 16에 스키마를 적용하고 일부 제약·조회 경계를 시험한 범위는 [검증 기록](verification.md)을 따른다. 빈 DB 적용이 동시 접수·실제 작업 복구를 검증한 것은 아니다.
