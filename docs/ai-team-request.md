# AI 담당에게 요청할 업무

기준일: 2026-11-04 · 대상: AI 담당 1명 · 현재 단계: 콘텐츠 게시 기준 확정, v0 실제 추론 연결, 모델 승인 임계값·안전성 평가 미수락

학생 모델 가중치와 로컬 CPU 연결 모듈을 확인했다. 현재 v0는 모든 결과를 검토 필요로 처리한다. 아래 요청서의 기존 일정·Issue 초안과 별개로, 다음 인계는 독립 평가·정상 글 오탐/유해 글 누락·채택한 판정 경계·재현 가능한 모델 버전이다. [현재 연결 코드와 실행 결과](student-model-integration.md)를 함께 확인한다.

이 문서는 [AI 계약](ai-contract.md)을 작업 단위로 풀어 쓴 요청서다. 필드·오류·출시 조건의 기준은 AI 계약이며, 변경할 때는 일반 백엔드 담당과 함께 합의한다. 아래 Issue는 복사해서 등록할 초안이고 실제 GitHub에 등록하거나 팀원에게 전송한 것은 아니다.

라벨링은 확정한 [게시 허용과 차단 기준](content-policy.md)을 따른다. 자기 외모 고민·일반 취향·스타일 비평은 허용하고, 특정 학생·사적 개인의 외모 모욕·공개 망신·조롱 유도는 차단한다. 학생 실명 등 개인 식별 정보는 괴롭힘 여부와 별개로 익명 표현으로 수정하도록 한다.

## Gemini 경로를 채택할 때의 업무 변경

[Gemini 서버 검수 설계](gemini-moderation-design.md)를 구현하는 경우 아래 로컬 안전성 모델 납품 요청 대신 정책 프롬프트·출력 계약·독립 평가를 맡는다. 감정 분류는 기존 로컬 모델을 재사용할 수 있다. 백엔드는 외부 호출·비용/쿼터 원장·SUPPORT 우선·제재 비활성화·영수증과 화면 연결을 구현한다. 아래 일정과 요청문은 기존 로컬 모델 인계안이며 Gemini 구현·평가를 완료했다는 뜻이 아니다.

## 그대로 전달할 짧은 요청문

> 무드월 AI 파트를 부탁하고 싶어. 학생이 쓴 30자 이내 한국어 문장으로 **① 공개 적합성 판단, ② 감정 분류** 결과를 반환해 주면 돼.
>
> 공개 적합성은 직접적인 욕설 없이 특정 학생을 저격·비방·조롱하는 글을 다루는 게 핵심이야. 감정은 축하·기쁨·응원·설렘·피곤·슬픔·화남·중립으로 나눠 줘. 두 결과가 필요하다는 뜻이지 모델 두 개를 꼭 따로 만들라는 뜻은 아니야.
>
> 내가 QR·세션·금칙어 검사·제재·DB·큐·작업자 감시·게시 결정을 맡을게. AI 쪽에서는 라벨 지침, 모델, CPU에서 불러 쓸 Python 추론 모듈, 평가 결과와 실행 환경을 부탁해. 별도 모델 HTTP 서버는 지금 만들지 않아도 돼.
>
> 우선 10월 30일까지 실제 모델 없이 결과를 재현하는 fake adapter로 연결하고, 11월 3일까지 실제 모듈·고정 모델 파일·평가 결과를 인계하는 것을 목표로 하자. 모델 파일만 넘기기보다는 새 환경에서 실행할 수 있는 코드·설명·의존성·예문까지 같이 부탁해. 상세 기준은 이 문서와 AI 계약을 같이 보자.

## AI가 맡을 네 작업 묶음

| 작업 | 입력 | 출력 | 완료 조건 |
| --- | --- | --- | --- |
| 공개 적합성 판단 | 표시용 한국어 문장의 NFC 표현. 욕설 검색용으로 뭉갠 문자열을 주지 않음 | `safety.verdict` = `ALLOW/BLOCK/UNCERTAIN`, 점수와 허용된 사유 코드 | 학교 저격·비방·조롱의 라벨 지침, 분리된 평가 결과, 불확실·미지원 입력 처리 근거가 있음 |
| 감정 분류 | 같은 문장. 공개 적합성 결과와 분리된 판단 축 | 공개 가능한 경우 `emotion`의 라벨·점수·출처 | 8개 감정 정의·경계 예문·클래스별 평가가 있고, 정상 부정 감정만으로 차단하지 않음 |
| 추론 모듈 | `AnalysisInput`과 고정된 모델·토크나이저·설정 | 동기 `Analyzer.analyze()`의 `AnalysisResult` 또는 명시된 오류 | 모델을 한 번 로드한 뒤 반복 호출, CPU 실행, 버전 고정, 계약에 맞는 정상·실패 동작 재현 |
| 평가와 인계 | 고정 bundle, 학습/조정과 분리된 평가셋, 목표 CPU 환경 | 평가 보고서·측정 결과·실행 안내·fixture·artifact manifest | 일반 백엔드가 새 환경에서 실행을 재현하고, 지원 범위·오류·롤백 방법을 확인할 수 있음 |

화남·슬픔·피곤은 학생이 표현할 수 있는 정상 감정이다. 반대로 축하 문장도 특정 학생을 조롱하면 부적절할 수 있다. 기존 기획의 ‘부적절’은 감정 라벨에 섞지 않고 공개 적합성 축에서 다룬다.

안전성 사유 코드에는 여러 범주가 있지만 **코드가 있다는 사실은 해당 탐지가 구현·검증됐다는 뜻이 아니다.** 이번 핵심은 저격·비방이며, 개인정보·혐오·성적 내용·위협 등은 AI 담당이 지원 가능 여부와 평가 근거를 보고하고 팀이 공개 운영 범위를 합의한다. 미지원 영역은 무조건 안전하다고 처리하지 않고 계약의 `UNCERTAIN` 처리 정책을 적용한다.

## 입력과 반환 예시

모델에는 문장만 전달한다. 쿠키·IP·학생 식별 정보·DB 제출 ID는 모델 입력에 넣지 않는다. 아래는 내부 AI 계약이며 학생에게 내려주는 HTTP 응답 형식과 다르다.

```json
{"schema_version": "1", "text": "오늘 시험 끝났다!"}
```

```json
{
  "schema_version": "1",
  "model_bundle_version": "moodwall-ko-v1",
  "inference_policy_version": "ko-short-1",
  "safety": {"verdict": "ALLOW", "score": 0.97, "reason_codes": []},
  "emotion": {"label": "JOY", "score": 0.86, "source": "MODEL"}
}
```

예시 점수는 성능이나 확률을 주장하는 값이 아니다. 점수 의미와 판정 경계는 모델별로 문서화한다. `BLOCK/UNCERTAIN`이면 사유 코드가 필요하고 `emotion`은 `null`이다. `ALLOW`이면 감정 결과가 필요하며, **안전성 ALLOW가 확인된 뒤 감정만 실패했을 때만** `NEUTRAL`, `score: null`, `source: FALLBACK`을 반환한다. 안전성 오류나 전체 모델 실패를 중립 감정으로 바꿔 게시하지 않는다.

일반 백엔드는 `BLOCK/UNCERTAIN`을 재작성 안내로 바꾸며, AI 판단만으로 경고·정지를 누적하지 않는다. 최종 상태·시간 제한·제재는 [AI 계약의 판정표](ai-contract.md#5-최종-판정은-백엔드가-수행)를 따른다.

AI 담당은 `model_bundle_version`·`inference_policy_version`을 관리하고, 일반 백엔드는 `moderation_policy_version`·`lexicon_version`을 관리한다. 전체 배포 manifest에는 양쪽이 확정한 값을 모으며 AI 담당이 게시·제재·사전 정책 버전을 임의로 정하지 않는다.

## 복사해서 만들 GitHub Issue 5개

### 1. `[AI] 라벨 지침과 공통 스키마·fake adapter 제공`

- 담당: AI. 검토: 일반 백엔드. 목표: 10월 29~30일.
- 할 일: 확정한 게시 기준에 따라 공개 적합성·감정 라벨과 애매한 예문을 정리하고, 계약의 Pydantic 스키마와 fake adapter를 제공한다.
- 완료 조건: 정상·차단·불확실·감정만 실패·전체 오류·지연을 재현하고, 실제 모델 없이 일반 백엔드/프론트 흐름을 연결할 수 있다. fake는 운영에서 사용하지 않는다.

### 2. `[AI] 저격·비방 문맥 판단 구현과 평가`

- 담당: AI. 라벨 검토: 팀. 목표: 10월 31일~11월 2일 첫 버전.
- 할 일: 직접 욕설이 없는 비방·특정 학생 조롱과 정상 부정 감정·자기 외모 고민·일반 취향·스타일 비평을 구분할 데이터와 라벨을 준비한다. 긍정적인 이름 언급도 학생을 식별하면 개인정보 수정 요청으로 구분하며 괴롭힘으로 오표기하지 않는다. 감정 데이터만으로 비방 탐지가 완성됐다고 보지 않는다.
- 완료 조건: `ALLOW/BLOCK/UNCERTAIN`과 사유 코드를 계약대로 반환하고, 정상 글 오차단·유해 글 누락·불확실 비율 및 실패 예문을 보고한다. 추가 안전성 범주는 지원/미지원 범위를 명시한다.

### 3. `[AI] 8개 감정 분류와 감정 실패 동작 구현`

- 담당: AI. 목표: 10월 31일~11월 2일 첫 버전.
- 할 일: 계약의 8개 영문 라벨로 분류하고 감정 경계 예문을 정한다. 애니메이션 효과 코드는 만들지 않는다.
- 완료 조건: 감정 macro-F1·클래스별 혼동을 보고하고, `ALLOW` 후 감정만 실패하는 경우의 fallback을 재현한다. 두 모델 또는 공유 모델 구조 선택 근거를 기록한다.

### 4. `[AI] CPU 추론 모듈·고정 artifact 인계`

- 담당: AI. 연결·배포: 일반 백엔드. 목표: 11월 3일 연결 gate.
- 할 일: 제안 위치 `backend/inference/`에 실행 모듈·명령행 예제를 제공하고, 학습 재현 코드는 `training/`에 구분한다. 별도 HTTP 서버·큐 소비자·watchdog는 AI 범위에 추가하지 않는다.
- 완료 조건: CPU 설치/실행 명령, Python·패키지 잠금, 모델/토크나이저/설정, label ID 순서, SHA-256, bundle·추론 정책 버전, 전처리·임계값, 데이터/모델 출처·사용 범위가 함께 전달된다. 큰 가중치·데이터는 Git에 직접 넣지 않고 배포 전에 준비하는 경로와 무결성 확인 방법을 기록한다.

### 5. `[AI] 분리 평가·서버 측정·통합 인수 지원`

- 담당: AI가 모델 평가·측정, 일반 백엔드가 큐·종료·늦은 결과·게시 통합 시험. 목표: 11월 3일 인계, 11월 4일 검증, 11월 5일 수락 확인.
- 할 일: 학습/조정 데이터와 최종 평가 데이터를 분리하고, 정상·오류 입출력 fixture 및 알려진 실패 유형을 제공한다. 목표 CPU의 사양·스레드 수와 p50/p95 지연, 최대 메모리, 콜드스타트를 기록한다.
- 완료 조건: 일반 백엔드가 새 환경에서 동일 bundle로 실행·회귀 검사를 재현하고, 60초 실행/120초 접수 예산 안에서 동작하는지 함께 확인한다. 팀이 평가 결과·허용 오차·지원 범위를 검토하고, 이전 bundle로 돌아가는 방법도 확인한다. 임의의 정확도 합격선을 추가하지 않는다.

## AI 담당과 먼저 확인할 네 가지

1. **데이터:** 지금 확보한 감정/비방 데이터와 사용 조건은 무엇이며, 학교 말투 예문은 누가 어떤 기준으로 라벨링할 수 있나?
2. **라벨:** 확정한 게시 기준에 따라 저격·외모 조롱과 정상 감정·취향·비평, 학생 식별 정보 수정 요청을 구분하고 애매한 문장을 `UNCERTAIN`으로 처리할 수 있나?
3. **CPU:** 현재 모델을 CPU에서 실행해 봤나? 측정 환경과 메모리·지연은 어느 정도이며, 서버 측정에 필요한 자원은 무엇인가?
4. **지원 범위·일정:** 비방 외 안전성 범주 중 실제로 평가 가능한 것은 무엇이고, 11월 3일에 실행 모듈·고정 artifact·평가 보고서를 함께 전달할 수 있나?

일정은 목표이며 성능·출시 보장이 아니다. 11월 3일 인계가 어렵거나 검증을 통과하지 못하면 즉시 팀에 공유한다. 11월 5일에 실제 학생 글을 미검수로 자동 공개하지 않으며, 필요하면 팀이 검토한 합성 예문을 쓰는 제한된 데모로 진행한다. 전체 일정은 [구현 계획](implementation-plan.md)을 따른다.
