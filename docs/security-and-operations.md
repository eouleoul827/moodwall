# 보안·개인정보·배포·운영 기준

기준일: 2026-10-29. 이 문서는 구현 전의 결정과 검증 항목이다. 보안 인증을 받았거나 가용성·처리량을 측정했다는 뜻이 아니다. 아래의 시간·보관 기간·요청 제한은 Moodwall 초기 정책이며, 일반 웹 서비스에 공통으로 강제되는 수치는 아니다.

## 1. 지켜야 하는 경계

초기 범위는 학교 한 곳, 전광판 한 대, 익명 학생 참여다. 쿠키는 브라우저를 다시 알아보기 위한 수단이다. 학생 한 명·물리 기기 한 대를 증명하지 않는다. 쿠키 삭제·다른 브라우저를 이용한 우회는 남고, QR 사진 공유도 완전히 막을 수 없다. 이 한계를 서비스 설명과 운영자 안내에 포함한다.

| 자격 | 허용 | 금지 |
|---|---|---|
| 익명 브라우저 세션 | 현재 입장 허가 확인, 자기 사용량·제출 상태 조회, 유효한 입장 후 제출 | 다른 사람의 제출 조회, 현재 QR 직접 수신, 전광판 제어, 운영자 기능 |
| 등록된 전광판 장치 | 자기 전광판의 QR·공개 화면·SSE 수신, heartbeat, MOODWALL·CHATBOT 전환 | PAUSED 설정·해제, 차단 원문·위반 상세 조회, 숨김·제재 복구, 운영자 계정 관리 |
| 운영자 세션 | ADMIN은 전체 운영, MODERATOR는 검수 조회·숨김·제재 복구 | 다른 사람과 계정 공유, 감사 기록 우회, MODERATOR의 장치·모드·접수·감사 관리 |
| 검수 작업자 | 지정된 검수 작업 읽기·결과 확정 | 공개 인증 API·학생 세션 처리, 임의 외부 URL·모델 코드 실행 |

서버가 매 요청에서 자격·대상 전광판·소유 관계를 검사한다. UUID를 안다고 읽을 수 있게 만들지 않는다. 제출 상세는 `submission.participant_id == authenticated_participant.id` 조건으로 조회하고, 남의 ID와 없는 ID는 동일한 404 응답으로 처리한다. 원칙은 기본 거부와 최소 권한이다. [OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)

운영자 역할은 DB의 ADMIN·MODERATOR다. 초기에는 ADMIN 한 계정으로 시작할 수 있고, 필요할 때 MODERATOR를 추가한다. 로그인·로그아웃·자신의 CSRF 조회는 양쪽 역할 모두 가능하다.

| 운영 동작 | ADMIN | MODERATOR |
|---|---|---|
| 장치 등록 코드 발급·장치 해지 | 허용 | 거부 |
| 화면 모드·송출 중단·접수 중단 | 허용 | 거부 |
| 제출 목록·상세 검수 조회·참여자 현재 사용량 조회 | 허용 | 허용 |
| 글 숨김·일일 제재 복구 | 허용 | 허용 |
| 운영자 감사 기록 조회 | 허용 | 거부 |

권한 검사는 동작뿐 아니라 응답 필드에도 적용한다. ORM 행 전체를 직렬화하지 않고 다음 DTO의 허용 필드만 응답한다. 입력 DTO도 추가 필드를 거부하므로 학생이 `participantId`, `moderationStatus`, `strikeApplied`, `role`을 넣어도 상태를 바꿀 수 없다. [OWASP API3: 속성별 권한](https://api-security.owasp.org/editions/2023/en/0xa3-broken-object-property-level-authorization/)

| 응답 대상 | 포함 | 제외 |
|---|---|---|
| 학생 본인 제출 | 본인 원문·상태·표시 상태·고정 안내, 승인 시 감정·애니메이션 | 다른 참여자의 원문, 규칙 매칭 위치, 모델 점수·내부 사유·실행 번호 |
| 전광판 state·SSE | 오늘 승인되었고 숨김·만료되지 않은 표시 항목, 공개 표시용 ID·감정·이모지, 상태 변경 신호 | 참여자 ID, 거절·검수 중 원문, 위반 수·정지, 모델 버전·점수·내부 사유 |
| 검수 권한 운영자 | 검수에 필요한 원문·참여자 ID·고정 사유·버전·제재 적용 여부 | 쿠키·세션 해시·IP·비밀번호·서명 키·작업자 실행 비밀 |
| ADMIN 감사 조회 | 행위자·동작·대상·사유 코드·시각 | 학생 원문, 인증 비밀 |

장치가 숨김 전 원문을 이미 받은 경우 원격으로 그 사본을 회수할 수는 없다. 숨김 뒤에는 최신 state에서 제외하고 정상 클라이언트가 화면과 메모리의 해당 항목을 제거하는 것을 검증한다. 서버와 브라우저의 정책은 별개로 확인한다.

## 2. 세션과 쿠키

학생·운영자·장치는 서로 다른 자격이다. 동일한 문자열을 세 역할에 재사용하거나, 클라이언트가 보낸 `participantId`·`role`을 신뢰하지 않는다.

| 구분 | 쿠키 예시 | 서버 저장 | 초기 만료 |
|---|---|---|---|
| 학생 | `__Host-mw_session` | 무작위 토큰의 해시, 참여자 ID, 절대 만료, 대상 전광판·입장 기한 | 발급 후 30일 |
| 운영자 | `__Host-mw_operator` | 무작위 토큰의 해시, 운영자 ID, 절대·유휴 만료 | 절대 8시간, 유휴 30분 |
| 전광판 | `__Host-mw_display` | 무작위 토큰의 해시, 대상 전광판, 만료·등록 시각 | 마지막 사용 후 180일(사용 중 하루 한 번 연장), 재등록·운영자 해지로 교체 |

인증 토큰은 CSPRNG로 만든 32바이트 이상의 값이다. 서버에는 SHA-256 등의 해시만 저장하고 토큰 원문을 로그에 남기지 않는다. 고엔트로피 토큰을 해시하는 것과 사람이 정한 비밀번호를 저장하는 것은 구분한다. 비밀번호는 아래의 Argon2id를 사용한다.

운영 쿠키는 `Secure; HttpOnly; SameSite=Lax; Path=/`를 사용하고 `Domain`을 지정하지 않는다. 운영 환경의 모든 통신은 HTTPS다. 쿠키 `Max-Age`뿐 아니라 서버 DB의 만료·해지 여부도 검사한다. 인증 토큰은 localStorage·URL·React 빌드 결과에 넣지 않는다. 로그인 때 운영자 세션을 새로 발급하고, 로그아웃·비밀번호 재설정 때 관련 세션을 해지한다. [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

30일 학생 수명은 절대 만료이며 QR 재교환·heartbeat·polling으로 늘리지 않는다.

**전광판 장치는 2026-11-10부터 슬라이딩 만료다.** 이전에는 학생과 같은 30일 절대 만료였다. 그래서 도서관 직원이 한 달마다 운영자 휴대폰과 등록 코드로 재등록해야 했고, 놓치면 전광판이 로고 화면에 멈췄다. 이제는 다음과 같이 동작한다.

- heartbeat가 오면 서버가 만료를 `now + 180일`로 옮긴다. 쓰기는 하루에 한 번만 한다(`DISPLAY_RENEW_EVERY`).
- 화면을 켤 때마다 `GET /api/display/session`이 같은 토큰의 쿠키를 같은 수명으로 다시 내려준다.
- 따라서 180일(방학을 넘는 기간) 동안 한 번도 켜지 않았을 때만 재등록이 필요하다.

이 결정의 근거는 다음과 같다.

- 장치는 직원이 관리하는 도서관 안의 노트북 한 대이고, 전용 브라우저 프로필에서 HttpOnly 쿠키로만 쓰인다.
- 전광판 권한으로 할 수 있는 일은 승인된 글 표시와 QR 받기뿐이다.
- 분실·의심 시에는 운영자 화면의 장치 해지(`revoke_display`)가 즉시 무효화한다. 만료된 토큰은 heartbeat로 되살리지 않는다.

학생 세션 만료 뒤에는 유효 QR로 새 익명 세션을 만들며, 이미 만료된 세션과 같은 사람임을 복구하는 기능은 없다. 학생 식별의 장기 유지에는 이 한계와 쿠키 삭제 우회가 남는다. 학생의 짧은 작성 권한은 별도 입장 기한으로 제한한다. 익명 식별에 30분 유휴 로그아웃을 적용해 새 참여자를 계속 만드는 방식은 쓰지 않는다. 이는 익명 재식별과 무인 장치 운영을 위한 프로젝트의 선택이며 일반적인 로그인 세션 권고 전체를 충족한다고 주장하지 않는다.

운영자 유휴 시간은 성공한 권한 있는 상태 변경 POST만 갱신하고, GET 목록·세션 확인·자동 polling은 갱신하지 않는다. 읽기 작업만 30분 계속해도 재로그인한다. 절대 8시간 제한은 어떤 요청으로도 연장하지 않는다. 장치 자격을 등록한 노트북에는 운영자 쿠키를 계속 남겨 두지 않고 로그아웃한다. 개발용 HTTP 예외는 로컬 설정에만 두며 운영 설정에 전파하지 않는다.

유효성은 요청마다 서버에서 확인한다. 운영자는 세션의 `revoked_at`·절대/유휴 만료뿐 아니라 현재 계정의 활성 여부와 역할도 DB에서 읽으므로 계정 비활성화·역할 변경을 옛 세션에 계속 허용하지 않는다. CLI 비밀번호 복구·비활성화는 해당 운영자의 모든 세션을 같은 트랜잭션에서 해지한다. 학생 사고 대응은 대상 참여자의 모든 browser session을 해지하고, 장치는 현재 토큰을 폐기하면서 heartbeat 임대도 종료한다. 만료·해지·불명 쿠키에는 401과 같은 이름·Path·Secure 속성의 `Max-Age=0` 쿠키를 반환한다. 쿠키를 지우는 것만으로 서버 해지를 대신하지 않는다.

인증 미들웨어가 만든 문맥만 믿고 오래 기다린 뒤 쓰기 작업을 실행하지 않는다. 기존 학생의 입장 갱신·신규 제출은 참여자 잠금 안에서 같은 세션의 소유·만료·해지 상태와 입장 기한을 재확인한다. 학생 세션 회수·삭제도 참여자부터 잠가 갱신·접수와 순서를 맞춘다. 장치의 heartbeat·모드 변경은 board 잠금 뒤 현재 장치 hash·version·만료를 재확인하고 장치 교체·회수도 같은 board 잠금을 사용한다. 회수가 먼저 확정되면 뒤의 옛 자격으로 변경하지 못한다. 이미 유효하게 수락된 제출은 세션 회수만으로 취소하지 않으며 필요한 취소·정지는 별도 정책을 적용한다.

운영자 변경 요청은 업무 잠금을 획득한 뒤 현재 계정 역할·활성 여부·세션 유효성을 다시 검사한 시점을 권한 판정 기준으로 삼는다. 그 검사보다 먼저 완료된 해지·역할 축소는 반영하며, 검사 시 유효했던 진행 중 요청은 이후 세션이 회수되더라도 완료될 수 있다. 이미 수락한 요청의 전면 취소까지 권한 회수의 의미로 약속하지 않는다. 임의 권한 캐시로 새 요청까지 허용하지 않는다.

DB 시각과 API의 timestamp는 UTC로 저장·ISO 8601로 전달하고, 하루 정책의 `businessDate`만 Asia/Seoul로 서버가 계산한다. 클라이언트 시계·시간대·요청 본문 날짜로 횟수·제재·입장 유효성을 정하지 않는다.

## 3. QR 입장과 기존 접속

QR URL은 `/join#ticket=...`를 사용한다. fragment는 HTTP 요청 URL로 보내지지 않는다. 프론트는 처음에 값을 읽고 즉시 주소에서 제거한 다음, JSON 본문으로 입장 API에 보낸다. 분석 스크립트·오류 보고 도구에도 ticket을 보내지 않는다. 쿼리 방식으로 변경한다면 프록시·애플리케이션의 URL 로그 마스킹까지 별도로 검증해야 한다.

서명된 QR에는 목적, 전광판 ID, 유효 시작·종료 시각, 서명 버전·키 ID를 포함한다. 검증 라이브러리를 사용하고 허용 알고리즘을 서버에서 고정한다. 서명만 맞는 것이 아니라 목적·전광판·시각·활성 키도 확인한다. 학생 세션이나 운영자 비밀은 넣지 않는다.

### 서명 형식과 키 교체

초기 형식은 검증된 JOSE 라이브러리의 compact JWS/JWT이며 암호화를 뜻하지 않는다. QR payload는 누구나 읽을 수 있으므로 학생 정보는 없다. JWT는 QR에만 사용하고 기존의 불투명 세션 쿠키를 JWT로 바꾸지 않는다. 알고리즘 고정·용도 분리·issuer/audience 검사 원칙은 [RFC 8725](https://www.rfc-editor.org/rfc/rfc8725.html), HS256의 키 길이 기준은 [RFC 7518 §3.2](https://www.rfc-editor.org/rfc/rfc7518.html#section-3.2)를 따른다. 아래 상수와 시간 창은 Moodwall의 계약이다.

| 위치 | 필수값·검증 |
|---|---|
| protected header | `alg=HS256`, `typ=mw-qr+jwt`, 배포 설정의 활성 목록에 존재하는 `kid` |
| claims | `iss=moodwall`, `aud=moodwall-qr-exchange`, `purpose=board-admission`, `v=1`, 실제 전광판의 `boardId` |
| 시간 | 정수 Unix 초 `iat=nbf=300초 구간 시작`, `exp=iat+600`. `nbf <= serverNow < exp`, iat는 현재·직전 구간 중 하나 |
| 서명 키 | CSPRNG 32바이트 이상, QR 전용. CSRF 키·DB 자격과 재사용하지 않음 |

헤더의 알고리즘을 보고 검증 방식을 선택하지 않고 `HS256`만 허용한다. `none`, 다른 알고리즘, 모르는 `kid`, 지원하지 않는 `crit` 헤더, 누락·변조 claim은 거부한다. `kid`는 메모리의 고정 key map에서만 찾고 파일 경로·SQL·외부 `jku`/`x5u` 주소를 조회하지 않는다. QR 입력 길이도 2 KiB 이내로 제한하고 무제한 토큰을 파싱하지 않는다. 이 시간 계약에는 추가 leeway를 두지 않으며 운영 서버의 UTC 시각 동기화를 확인한다.

평상시 키 교체는 새 검증 키 배포 → 새 `kid`로 발급 전환 → 마지막 구 키 발급 ticket의 `exp` 이후 구 키 제거 순서다. 구 키 검증 공존은 마지막 발급 후 최대 10분이며 QR의 유효 기한을 연장하지 않는다. 키 유출 때는 유예하지 않는다. 단일 API를 유지보수 중단한 상태에서 구 키를 제거하고 새 키로 재시작한 뒤 해당 전광판의 기존 `admission_*` 필드를 모두 NULL로 지우고 접수를 재개한다. 이때 학생 식별·작성 횟수·제재는 지우지 않고 최신 QR 재스캔을 요구한다. 서명 키 제거만으로 이미 교환된 DB 입장 허가가 자동 취소된다고 가정하지 않는다. 키 목록·교체 시각·작업자를 비밀값 없이 배포 기록에 남긴다. [OWASP Key Management](https://cheatsheetseries.owasp.org/cheatsheets/Key_Management_Cheat_Sheet.html)

- QR은 5분마다 교체하고, 현재 QR과 직전 QR을 모두 인정한다. 각 ticket은 `issuedAt + 10분`까지 유효하다. 별도 30초 유예는 없다. 서버 요청 도착 시각을 기준으로 한다.
- 서버가 유효 시각을 확인하므로 사용자마다 직전 QR 목록을 저장하지 않는다.
- 공개 QR은 여러 명이 사용하는 입장 티켓이다. 첫 학생이 사용했다고 폐기하지 않는다.
- 교환 성공 시 세션에 대상 전광판과 `admission.expiresAt = ticket.validUntil`을 기록한다. 교환 시점부터 10분이 아니라 원래 ticket 종료 시각이다.
- QR 교체는 이미 받은 허가·참여자·횟수·제재를 바꾸지 않는다.
- 새 QR을 찍어도 같은 학생 쿠키가 있으면 기존 참여자를 사용하고 해당 새 ticket의 기한으로 허가를 갱신한다. 오래된 ticket을 다시 교환해 기존 허가를 더 짧게 줄이지 않는다.
- 만료 QR만으로 입장 허가를 연장하지 않는다. 유효한 기존 허가가 있으면 작성 화면은 계속 쓸 수 있다.
- 브라우저 새로고침·heartbeat·멘션 작성만으로 허가를 자동 연장하지 않는다. 허가가 끝나면 입력 초안은 남기고 QR 재스캔을 안내한다. 30일 세션 수명과 이 입장 기한은 별개다.

현재 QR API는 등록된 장치만 호출한다. 학생용 응답·공개 정적 JSON·공개 SSE에는 현재 ticket을 넣지 않는다. 누군가 화면을 촬영해 공유하는 공격까지 막는다는 의미는 아니다.

### LTE·5G 허용과 최근 QR 제한

MVP는 학교 Wi-Fi·LTE·5G를 모두 허용한다. 최근 QR을 가진 브라우저에만 짧은 입장 허가를 주는 best-effort 방식으로 확정한다. QR은 5분마다 교체하며 현재·직전 ticket을 인정하고, 각 ticket의 발급 후 10분에 허가도 끝난다. 학교 IP 허용 목록이나 학교망 설정을 출시 조건으로 요구하지 않는다.

유효한 QR 사진·링크가 공유되면 교외에서도 남은 유효 시간 안에 입장·작성할 수 있다. 따라서 최근 QR 참여 제한은 현장 방문이나 현장 체류의 증명이 아니고 교외 차단을 보장하지 않는다. 학교 Wi-Fi에서 LTE로 바꾸어도 세션·입장 기한·작성 제한은 유지한다. IP는 보조 트래픽 보호 신호이며 개인 식별이나 현장 증명에 사용하지 않는다.

향후 학교망만 허용하는 strict 모드를 선택할 수 있지만 LTE·5G 참여도 차단하므로 별도의 정책 변경으로 다룬다.

## 4. CSRF와 브라우저 요청

웹과 API는 같은 HTTPS origin에서 제공한다. 상태 변경은 POST 등으로 처리하고 GET에 제출·숨김·모드 변경을 넣지 않는다. `SameSite`나 CORS 설정만으로 요청 권한 검사가 끝났다고 보지 않는다. [OWASP CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)

| 요청 | 검사 |
|---|---|
| 첫 QR 교환·첫 운영자 로그인·첫 장치 pairing | 정확한 허용 `Origin`, JSON content type, 요청 크기·속도 제한, 각 자격 증명 |
| 기존 학생 세션의 새 제출·입장 갱신 | 위 검사 + 학생 세션에 묶인 `X-CSRF-Token` |
| 운영자·장치의 상태 변경 | 위 검사 + 해당 역할 세션에 묶인 `X-CSRF-Token` |
| 학생 본인 상태·전광판 state·SSE | 역할·소유권 검사, 비공개 캐시 정책. 상태를 변경하지 않음 |

CSRF token은 서버 비밀과 실제 세션 쿠키를 입력으로 HMAC하여 생성하고 학생·운영자·장치 문맥을 구분한다. 토큰은 세션과 함께 검증하며 상수 시간 비교를 사용한다. 인증 쿠키와 달리 프론트가 token을 읽어 메모리에 둘 수 있다. 학생은 `GET /api/session`, 운영자는 인증 후 `GET /api/operator/session`, 장치는 `GET /api/display/session`으로 얻는다. 세션 쿠키 원문은 응답 본문에 보내지 않는다. 로그인·pairing·입장 교환의 성공 응답에도 해당 token을 포함한다.

첫 교환·로그인·pairing은 아직 세션 token이 없으므로 CSRF token 예외지만, 정확한 Origin과 JSON을 반드시 검사한다. `null`·누락 Origin을 자동 허용하지 않는다. 외부 페이지에서 가능한 form content type은 받지 않는다. 재교환 등 이미 세션이 있는 상태에서는 해당 CSRF token을 요구한다. 로컬 개발 origin은 명시적으로 열거하고 운영에서 wildcard credential CORS를 사용하지 않는다.

bootstrap 예외는 해당 역할 쿠키가 실제로 없는 요청에만 적용한다. 유효한 학생·운영자·장치 쿠키가 있으면 교환·재로그인·재등록도 기존 역할의 CSRF token을 검사한다. 만료·해지·불명 쿠키는 `401 SESSION_EXPIRED`로 그 쿠키를 지운 뒤 브라우저가 한 번 처음부터 다시 시도한다. 쿠키 자체가 없으면 `SESSION_REQUIRED`, 운영자 로그인 실패는 `INVALID_CREDENTIALS`로 구분한다. 프론트는 읽을 수 없는 Set-Cookie 대신 code로 분기한다. 반면 유효 쿠키의 CSRF 누락·불일치는 403이며 쿠키를 지우거나 새 참여자로 자동 교체하지 않는다. 이 구분을 프론트와 계약한다. CSRF 비밀을 교체하면 기존 쿠키의 세션 조회에서 새 token을 얻을 수 있고 참여자·사용량은 바뀌지 않는다. Origin 비교는 서버 설정의 `PUBLIC_ORIGIN`과 scheme·host·port 전체를 정확히 비교하며 요청의 임의 Host·Forwarded 값으로 허용 origin을 만들지 않는다.

입장·로그인·pairing 응답 유실은 쿠키 저장 여부와 별개의 문제다. 해당 역할의 session GET으로 성공 여부와 CSRF부터 확인하며 유효 쿠키가 있는데 무-CSRF bootstrap을 반복하지 않는다. 학생의 session이 없고 ticket이 아직 유효할 때만 최초 교환을 제한적으로 재시도한다. 장치 쿠키가 없다면 이미 소비한 pairing code를 재사용하지 않고 새 코드를 발급한다. 학생의 쿠키 저장이 계속 실패하면 반복 세션 발급을 멈추고 브라우저 안내를 표시한다. 동시 탭·외부 브라우저 전환은 익명 제한의 우회 가능성으로 남으며 IP나 지문으로 강제 합치지 않는다.

SSE는 장치 쿠키로 인증한다. 같은 origin의 `EventSource` GET에는 Origin 헤더가 없을 수 있으므로 상태 변경 POST와 달리 누락 자체로 거절하지 않는다. 헤더가 있다면 정확히 일치해야 하고 `Sec-Fetch-Site: cross-site` 요청은 거부한다. 운영에서는 cross-origin credential CORS를 열지 않는다. 인증 없는 GET이나 화면 진입은 새 세션·입장 권한을 만들지 않는다. [MDN Origin의 GET 예외](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Origin#description), [OWASP Origin 검증](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html#using-standard-headers-to-verify-origin)

세션·QR·제출·운영자·전광판 `/api` 응답은 성공과 오류 모두 `Cache-Control: no-store`를 사용한다. CDN은 `/api/*`와 `Set-Cookie` 응답을 우회하고 service worker·Cache API·오프라인 저장에서도 API를 제외한다. 초기에는 service worker를 도입하지 않는다. SPA HTML도 `no-store`, 파일명에 content hash가 붙은 공개 JS·CSS·정적 자산만 `public, max-age=31536000, immutable`로 캐시한다. `no-cache`는 저장 자체를 금지하지 않고 `no-store`도 브라우저의 모든 JS 저장소를 통제하지 않는다. 로그아웃 시 운영자 원문·세션 상태를 프론트 메모리에서 제거하고, 운영자 화면 진입·뒤로 가기 복귀 시 세션 재검증 전 원문을 표시하지 않는다. [OWASP HTTP Headers](https://cheatsheetseries.owasp.org/cheatsheets/HTTP_Headers_Cheat_Sheet.html#cache-control)

## 5. 중복 요청·도배·자원 고갈

학생 화면의 재시도는 같은 `Idempotency-Key`와 같은 본문을 사용한다. 서버는 유효한 소유 세션을 확인한 뒤 기존 기록을 먼저 찾는다. 같은 키·다른 내용은 409다. 같은 키의 기존 요청은 현재의 신규 입장·정지·횟수 제한 때문에 다시 거절하거나 재처리하지 않고 기존 상태를 반환한다. 세션이 만료되거나 소유 관계를 확인하지 못하면 다른 방식으로 본인을 주장하게 하지 않는다.

HTTP 크기·엄격한 JSON 구조·고정 v1 정규화는 먼저 검사하되 현재 emoji 활성 목록·금칙 정책은 새 요청에만 적용한다. 정책 변경으로 보관 기간 안의 기존 키 조회를 422로 바꾸지 않는다. 만료된 입장 허가를 재교환한 것이 기존 제출·제재를 재초기화하는 수단이 되지 않게 한다. UUID Idempotency-Key는 Moodwall의 계약이며 현재 IETF 초안의 다른 직렬화 규칙을 따른다는 의미가 아니다.

신규 요청에만 유효한 입장·당일 정지·시간당 작성량과 다음 보호를 적용한다.

- 참여자당 처리 중 검수는 최대 1개다.
- 새로운 유효 제출은 최소 10초 간격이다. 모델 수정 요청도 적용 대상이다.
- 참여자당 최근 60분의 승인 + 예약은 최대 3개다. 각 제출의 `accepted_at`을 기준으로 움직이는 구간이며 정각 초기화가 아니다. 거절·실패·만료는 슬롯을 반환한다. 이 계산은 DB에서 원자적으로 처리한다.
- 23:50에 승인된 글도 00:10의 최근 60분에 포함된다. 자정은 화면·일일 금칙 제재의 기준이며 시간당 작성 한도를 초기화하지 않는다.
- 동일 요청의 재시도는 위 업무 cooldown을 늘리지 않지만 HTTP 남용 방어는 적용한다.
- 검수 서비스 비정상·대기열 포화 때는 슬롯 예약 없이 503과 재시도 안내를 반환한다.
- 글자는 30개 제한과 별개로 HTTP 본문 바이트 상한도 둔다. 초기 제출 JSON 상한은 4 KiB다.
- 세션별 polling은 프론트 기본 2초 간격에서 시작하고 완료 시 중단한다. 서버는 과도한 polling에 429와 `Retry-After`를 반환한다.

학교 Wi-Fi의 많은 학생이 공인 IP 하나를 공유할 수 있다. 작성량·욕설 제재에서 IP는 대량 요청 탐지와 전체 서비스 보호의 보조 신호다. 개인의 시간당 3회·하루 금칙 5회 정지를 IP에 연결하지 않는다. 전체 IP 임계치는 실제 동시 접속·입장 부하를 측정해 정하고, 학교 전체가 막히는지 시험한다. 작은 숫자를 임의로 정해 개인 제한처럼 운영하지 않는다.

브라우저 지문은 초기 구현에서 제외한다. CAPTCHA·추가 인증도 실제 자동화가 확인되면 운영 수단으로 추가한다. 어떤 요청도 유효한 nonce나 idempotency key만으로 무제한 CPU·DB 사용을 허용하지 않는다.

## 6. 입력·출력과 AI 경계

문자열은 자유로운 유니코드 텍스트로 받되 보이는 글자 단위 길이, 바이트 상한, 빈 문자열·금지 제어 문자를 검사한다. 이모지는 서버가 제공한 `emojiId` 목록에서만 선택한다. 클라이언트가 전달한 CSS·HTML·외부 이미지 URL은 받지 않는다.

욕설 차단은 콘텐츠 정책이다. SQL injection이나 XSS를 막는 보안 장치로 취급하지 않는다. SQL은 파라미터 바인딩을 사용하고, 프론트는 학생 글을 텍스트로 출력하며 `dangerouslySetInnerHTML`을 사용하지 않는다. 정규식·정규화는 입력 상한 안에서 실행하고 오래 걸리는 조합을 시험한다. [OWASP Input Validation](https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html)

JSON POST는 기본 4 KiB 실제 수신 상한을 프록시·앱에서 검사한다. Content-Length가 없거나 분할 전송이어도 누적 상한은 같다. 초기에는 identity 외의 Content-Encoding을 415로 거절하는 프로젝트 정책을 사용한다. UTF-8·중복 JSON 이름·고립 surrogate·Unicode noncharacter·NaN·Infinity 검사를 공통 parser에 적용하고 알려진 필드와 엄격한 타입만 DTO에 넘긴다. 파싱·입력 오류에 원문이나 제재를 덧붙이지 않는다. 상태 코드와 정확한 순서는 [HTTP 입력 계약](backend-contracts.md)을 따른다. RFC 8259와 I-JSON의 해당 상호운용 제약을 채택한 것이며 임의 parser 기본값과 같다고 가정하지 않는다. [RFC 8259](https://www.rfc-editor.org/rfc/rfc8259.html), [RFC 7493 §2](https://www.rfc-editor.org/rfc/rfc7493.html#section-2)

HTTP 오류는 명세의 고정 오류 코드·안내·요청 ID로 응답하고 stack trace·SQL·내부 파일 경로를 보내지 않는다. FastAPI/Pydantic의 기본 validation error를 그대로 직렬화하지 않는다. 필요한 필드 경로·오류 종류만 추출하고 원래 `input` 값·예외 `ctx`는 응답과 로그에서 제외한다. 이 규칙은 비밀번호·pairing·QR과 학생 글의 검증 실패에도 적용한다. [OWASP REST 오류 처리](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html#error-handling)

정적 파일과 API에는 적절한 MIME type·`X-Content-Type-Options: nosniff`를 설정한다. 페이지에는 아래 헤더를 역방향 프록시에서 일관되게 보낸다. 초기 React 정적 빌드와 같은 origin의 API만 사용하는 전제의 프로젝트 기준이며, CSP의 일반적인 유일한 정답은 아니다. [OWASP CSP](https://cheatsheetseries.owasp.org/cheatsheets/Content_Security_Policy_Cheat_Sheet.html)

```text
Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self'; style-src-attr 'unsafe-inline'; connect-src 'self'; img-src 'self' data:; font-src 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'; form-action 'self'
X-Content-Type-Options: nosniff
Referrer-Policy: no-referrer
X-Frame-Options: DENY
Permissions-Policy: camera=(), microphone=(), geolocation=()
```

이 CSP는 nonce/hash 기반 strict CSP를 구현했다는 뜻이 아니다. React 애니메이션에 필요한 style 속성만 허용하고 inline script·event handler·eval은 허용하지 않는다. CSS-in-JS가 `<style>`을 삽입하는 라이브러리는 현재 정책에서 막힐 수 있으므로 정적 CSS를 우선 사용하고 staging의 실제 빌드로 확인한다. QR은 휴대전화 기본 카메라로 열며 앱 안의 카메라·마이크·위치 API는 사용하지 않는다. 먼저 staging에서 Report-Only로 위반을 조사한 뒤 운영에서는 enforced CSP로 배포한다. 보고 endpoint에 학생 원문·URL ticket을 수집하지 않는다. CSP는 텍스트 출력·권한 검사를 대체하지 않는다.

HSTS는 인증서·갱신·HTTP→HTTPS 전환을 검증한 뒤 처음에는 `max-age=86400`, 정상 운영 확인 뒤 `max-age=31536000`으로 올린다. 초기에는 `includeSubDomains`·preload를 넣지 않아 소유하지 않은 하위 서비스까지 묶지 않는다. 이 값은 단계적 도입 정책이다. 동적 API·장치 SSE·보호된 화면에도 프록시가 보안 헤더를 누락하지 않는지 확인한다.

검수 작업자에 필요한 학생 입력은 글 내용뿐이다. 쿠키·IP·학생 식별 메타데이터·QR은 모델로 보내지 않는다. 학생이 본문에 쓴 이름·별명은 포함될 수 있으므로 외부 모델 입력의 완전 익명화를 보장하지 않는다. 모델은 게시·제재·DB 변경을 직접 실행하지 않고 정해진 판정 결과만 반환한다. 출력은 enum·점수 범위·버전으로 검증한다.

확정 금칙 패턴만 위반 횟수를 올린다. 모델의 BLOCK·UNCERTAIN은 수정 요청이며 자동 위반이 아니다. 학생에게는 고정 안내와 상태만 보여 주고 내부 규칙·점수·차단 원문 목록을 보내지 않는다. 모델·서버 오류를 욕설 시도로 집계하지 않는다. 유해성 판정 실패를 정상 허용으로 바꾸지 않는다.

콘텐츠의 공개 경계는 [게시 허용과 차단 기준](content-policy.md)을 따른다. 정상 부정 감정·자기 외모 고민·취향·스타일 비평·가벼운 행동 비판·비하 없는 농담과 실명·별명 단순 언급을 허용한다. 특정 학생의 외모 모욕·공개 망신·따돌림 유도는 송출하지 않는다. 개인 학번·개별 반번호·연락처·민감 사생활 수정 요청과 자신의 위기·도움 요청은 게시 여부를 별도로 처리하며 자동 벌점 사유로 삼지 않는다. 위기 표현의 비공개 지원 안내를 실제 상담·자동 전달 기능으로 오인하게 안내하지 않는다.

모델 artifact는 AI 담당이 검증한 고정 버전·해시로 배포한다. 런타임에 학생이 지정한 경로·URL·가중치를 읽거나 원격 코드를 실행하지 않는다. 실제 학생 원문·실패 입력을 CI fixture, 개인 Colab, 자동 재학습으로 넘기지 않는다. 외부 API를 사용하는 별도 프로필은 [Gemini 서버 검수 설계](gemini-moderation-design.md)로 목적·전송 필드·보관·실패 경계를 정했다. 해당 구현 전 설계는 검수용 최소 문장과 trusted 탐지 플래그만 단일 요청으로 보내며, key·학생/학교 ID·과거 글·쿠키는 보내지 않는다. 이를 다른 공급자 반출이나 학습 허용으로 확대하지 않는다. 이번 문서 작업에서 실제 글을 외부로 전송하지 않았다.

Gemini 프로필은 위기 지원 여부를 확인하기 전에 로컬 욕설 결과로 제재를 확정하지 않고 전체 자동 벌점을 끈다. 기존 확정 규칙 제재 프로필과 구분한다. `store=false`를 모든 공급자 보관 0일로 설명하지 않으며, 원문·API 요청/응답 body·키·thought를 로그/APM에 복제하지 않는다. 세부 보관·정산·회로·사고 대응은 [Gemini 운영 설계](gemini-moderation-operations.md)를 따른다.

## 7. 운영자와 전광판 등록

운영자는 실명 공개가 아니라도 개인별 구분 가능한 계정을 쓴다. 공용 `admin/admin` 계정을 만들지 않는다. 초기 계정 생성·비밀번호 복구는 서버의 신뢰된 CLI로 수행하고 공개 회원가입·이메일 비밀번호 재설정 기능은 만들지 않는다. 명령행 인자·셸 기록에 평문 비밀번호를 넣지 않고 대화식 비밀 입력을 사용한다.

MFA를 사용하지 않는 초기 운영자 비밀번호는 생성·복구 CLI에서 15~128 Unicode 문자로 제한하고 널리 쓰이는 비밀번호·유출 비밀번호의 로컬 차단 목록과 비교한다. 목록의 출처·라이선스·버전을 기록하고 사용자 비밀번호를 외부 검사 서비스로 전송하지 않는다. 공백·유니코드·붙여넣기를 허용하고 조합 규칙이나 임의의 주기적 변경을 강제하지 않는다. 입력을 조용히 잘라내거나 trim하지 않으며 비밀관리자의 긴 무작위 비밀번호를 권장한다. 15자 최소와 64자 이상 최대 허용 원칙은 [OWASP 인증 지침](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#implement-proper-password-strength-controls)에 근거하고, 128자 상한은 이 프로젝트의 자원 보호 선택이다. 로그인 API의 길이 검사는 새 비밀번호 생성 규칙과 구분한다.

비밀번호는 검증된 라이브러리의 Argon2id로 해시한다. OWASP가 제시하는 최소 설정을 출발점으로 메모리 19 MiB, 반복 2, 병렬도 1 이상을 사용하고 서버 비용을 측정한다. 비밀번호는 원문·일반 SHA 해시·암호화 복호화 방식으로 저장하지 않는다. [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)

로그인은 계정·출처별 점진적 지연과 속도 제한을 적용하고 계정 존재 여부를 구분하지 않는 오류를 반환한다. 복구·운영자 비밀번호 변경 뒤에는 기존 세션을 해지한다. MFA나 학교 OIDC는 후속 보강 선택지이며, 현재 합의하지 않은 외부 서비스를 필수로 추가하지 않는다. [OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)

전광판 등록은 다음 순서다. 운영자 컴퓨터에서 다른 노트북의 쿠키를 직접 설정할 수 있다고 가정하지 않는다.

1. 로그인한 운영자가 `POST /api/operator/display/pairing-codes`를 호출한다.
2. 서버가 5분 유효한 32바이트 무작위 일회용 코드를 발급한다. DB에는 해시와 만료만 저장한다. 새 코드는 이전 미사용 코드를 취소한다.
3. 실제 전광판 노트북에서 등록 화면을 열고 코드를 붙여 넣는다.
4. `POST /api/display/pair`가 코드 해시·만료를 원자적으로 확인·소비하고 그 노트북에 장치 쿠키를 발급한다.
5. 기존 장치 자격은 새 등록과 동시에 무효화한다. 한 전광판에 활성 자격 하나만 허용한다.
6. 운영자가 `POST /api/operator/display/revoke`를 호출하면 장치 자격과 미사용 등록 코드를 해지한다.

pairing code 원문을 저장하거나 URL·로그에 넣지 않는다. 짧은 숫자 코드의 무제한 대입 방식으로 바꾸지 않는다. SSE 시작·이벤트 전송 직전과 이벤트가 없는 동안 최대 5초마다 현재 장치 토큰 해시·버전·만료를 DB에서 확인한다. 해지·만료가 확인되면 바로 닫고, 연결당 최대 5분에 도달해도 닫아 재인증한다. 해지 반영 목표는 건강한 API·DB에서 5초 이내이며 실제 시험 전에는 측정된 보장이 아니다. DB 확인 실패도 연결을 유지하며 계속 보내지 않는다. 브라우저 자동 재연결은 현재 자격을 다시 검사한다. 단순 메모리 캐시나 연결 시점의 인증만 믿고 해지된 장치에 이벤트를 계속 보내지 않는다.

운영자의 숨김·중단·제재 복구·등록 해지는 actor, action, 대상 ID, 시각, 사유 코드를 감사 기록에 남긴다. API 사유 필드는 자유 입력 `reason`이 아닌 `reasonCode`이며 `INAPPROPRIATE_CONTENT`, `FALSE_POSITIVE`, `MAINTENANCE`, `DEVICE_REPLACED`, `SECURITY_REVIEW`, `OTHER` 중 하나다. 학생 원문을 자유 입력 사유로 복사하지 않는다. DB에는 `reason_code`로 저장한다.

`POST /api/operator/daily-usage/{participantId}/{businessDate}/restore`는 `reasonCode`와 UUID `Idempotency-Key`가 필수다. 새 명령은 당일 한국 날짜의 제재 집계에 `banned_until=NULL`, `violation_count=0`을 감사 기록과 같은 트랜잭션에서 적용한다. 외부 JSON의 `suspendedUntil`은 DB `banned_until`을 매핑한 이름이다. 기존 제출 판정·`strike_applied`·감사 이력은 보존한다. 따라서 현재 제재 집계는 전체 과거 위반의 합과 다를 수 있다. 최근 60분 승인 이력은 지우지 않고 REJECTED 글도 공개하지 않는다.

감사 기록의 command_key·요청 hash와 `(operator_id, action, command_key)` UNIQUE로 복구 명령을 90일 중복 방어한다. 인증·권한 확인 뒤 기존 명령 조회를 당일 날짜 검사보다 먼저 수행하고 참여자·집계 잠금 뒤 다시 확인한다. 같은 대상·날짜·사유 hash면 재초기화 없이 현재 오늘 Usage를 돌려주고 다르면 409다. 다른 대상의 같은 키가 경쟁하여 UNIQUE에 걸리면 전체 롤백 뒤 기존 명령을 조회한다. 응답은 `{auditId, replayed, businessDate, usage}`이며 auditId와 businessDate는 원래 명령, usage는 응답 시점 오늘의 값이다. 자정 뒤 옛 명령을 확인해도 새날 집계를 초기화하지 않는다. 새 명령의 과거 날짜는 409 INVALID_STATE다. 보관 정리로 대상 참여자가 삭제된 경우는 404이며 새 참여자·가상 Usage를 만들지 않는다. 응답 유실 후 그 사이 새 위반이 발생한 상황에서 재전송이 새 위반을 지우지 않는지 시험한다. ADMIN·MODERATOR는 `GET /api/operator/participants/{participantId}/usage`로 현재 상태를 확인하며 다른 학생에게 이 API를 공개하지 않는다.

그 밖의 운영자 POST는 자동 재시도하지 않는다. 이미 HIDDEN인 글의 숨김 재호출은 200·감사 중복 없음으로 수렴한다. pairing-code 발급은 다시 실행하면 이전 미사용 코드를 교체하며, 응답 유실 때 자동 반복하지 않는다. 운영자 감사 응답의 이전·이후 위반 수와 정지 시각은 nullable이며 해당 행위에 값이 없는 경우 null로 제공한다.

장치는 `POST /api/display/mode`로 자기 전광판의 MOODWALL·CHATBOT만 전환한다. 운영자는 별도 `POST /api/operator/board/mode`로 모드와 송출 중단을 제어한다. 운영자가 PAUSED로 둔 동안 장치의 모드 변경은 `409 BOARD_PAUSED`로 거부하고 운영자만 재개한다. 자격의 `set_own_mode`는 운영자 권한으로 승격되지 않는다.

DB는 `mode=MOODWALL|CHATBOT`과 별도 `display_paused`를 저장한다. API는 둘을 합친 유효 화면 모드를 `MOODWALL|CHATBOT|PAUSED`로 제공한다. PAUSED는 세 번째 DB mode가 아니다. 화면 중단과 새 글 접수 중단도 구분한다. ADMIN이 `POST /api/operator/board/intake`에 `{paused, reasonCode}`를 보내 접수를 중단·재개하며, 신규 접수만 중단한다. 이미 소유한 요청의 재조회·동일 키 재시도는 계속 가능하다. 신규 접수가 gate를 읽은 뒤 pause가 커밋된 경합에서는 그 접수가 완료될 수 있다. 긴급 송출 중단과 달리 진행 중 트랜잭션의 일괄 취소를 보장하지 않는다. 정책상 기존 검수·대기·표시를 취소하는 동작도 아니다.

|---|---|---|
| 승인·차단 제출 원문과 검수 결과 | 서버 접수 후 1시간 | 만료부터 서버 조회 제외, 약 5초 주기 작은 배치로 제출 행과 원문 삭제. 전광판 당일 사본과 구분. 정리 장애·잠금 경합 시 지연 감시 |
| 전광판이 받은 공개 카드의 원문·이모지·감정 | 다음 KST 자정까지 | 전용 노트북의 당일 localStorage·메모리에서 투명 말풍선으로 유지. 자정·명시적 숨김·기기 세대 변경 때 삭제. 미실행 중 자정은 다음 시작 때 정리 |
| idempotency 결과·요청 fingerprint | 동일 1시간 | 이후 재시도 재현 보장 없음. 같은 키가 새 요청이 될 수 있으므로 프론트는 오래된 요청을 자동 재전송하지 않음 |
| 학생 세션 | 발급 후 30일 | 만료 후 해지·삭제. 살아 있는 세션이 없는 참여자는 참조 정리 후 삭제 가능 |
| 일일 금칙 제재 집계 | 해당 날짜 후 30일 | 당일 제재와 진행 중 작업을 먼저 정리. 최근 60분 한도는 제출 이력으로 별도 계산 |
| 애플리케이션 접근·오류 로그 | 14일 | 기본은 요청 ID·경로 템플릿·결과·소요 시간·안전한 오류 코드 |
| 운영자 감사 기록·제재 복구 명령 키/hash | 90일 | 원문·인증 비밀 없음. 이 기간의 복구 명령 재전송은 재초기화하지 않음 |
| 암호화된 백업 | 7일 순환 | 운영 DB에서 삭제된 원문도 이미 생성된 백업에서 해당 백업 만료까지 최대 7일 남을 수 있음 |

서버 DB 삭제는 전광판의 당일 말풍선 삭제와 다르다. `expiresAt=accepted_at+1시간`은 오프라인·대기와 무관한 DB 원문 보관 종료다. 이미 전광판에 받은 원문은 `ambientUntil`인 다음 KST 자정까지 남으므로 학생 안내에도 DB 1시간·전광판 당일 사본을 구분한다. 원문 삭제 시 정규화본·처리 결과의 원문 사본·종료된 큐 payload·첨부 로그도 점검한다. 큐 payload는 제출 ID 중심으로 만들고 Procrastinate의 종료 작업 정리도 포함한다. SQL DELETE는 활성 DB 행 삭제이며 전광판 localStorage·백업·WAL·디스크의 즉시 물리 덮어쓰기까지 뜻하지 않는다. 백업 복구 후 현재 보관 정책의 정리를 재실행하고 복구 시각을 기록한다.

일반 로그에는 쿠키·Authorization·CSRF·QR·pairing code·비밀번호·요청 본문·학생 원문을 기록하지 않는다. 오류 추적 도구의 body·header 자동 수집도 비활성화한다. IP가 필요한 단기 보안 조사와 기본 서비스 로그는 목적을 나누며, IP로 장기 개인 프로필을 만들지 않는다. [OWASP Logging](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)

수집 목적은 짧은 시간의 멘션 공개 서비스다. 화면에 원문 보관 기간과 공개 표시 사실을 안내한다. 실명·별명의 단순 언급은 허용하되 개인 학번·개별 반번호·연락처·집 주소·민감한 사생활을 쓰지 않도록 작성 화면에서 안내하고, 운영자는 공개 제한 정보를 숨길 수 있다. 자동 재학습을 하지 않으며, 익명 세션이라고 원문도 자동으로 익명 정보가 된다고 가정하지 않는다.

## 9. 배포 구성과 비밀 관리

초기 운영은 Linux VM 한 대의 Docker Compose와 관리형 PostgreSQL을 사용한다. 학생·전광판·운영자 브라우저는 같은 서비스 도메인으로 접속한다. 전광판 노트북에는 서버·DB·학습 코드를 설치하지 않는다.

```text
인터넷 HTTPS
    ↓
역방향 프록시: TLS, React 정적 파일, /api 전달
    ├─ API 프로세스 1개: 접수·권한·SSE·표시 조정·기한 정리
    └─ 검수 supervisor/작업자 1개: 모델 로드·추론·판정 확정
                ↓
       관리형 PostgreSQL: 상태·사용량·작업 큐
```

API에는 모델을 올리지 않는다. API와 작업자에 CPU·메모리 상한을 두고, 모델 메모리가 VM 전체를 고갈시키지 않는지 확인한다. API worker를 임의로 늘리면 조정 작업이 중복 실행될 수 있으므로, 증가 전에 분산 리더·DB 잠금 설계를 다시 확인한다. 단일 VM은 고가용성 구성이 아니며 VM 장애 시 서비스를 사용할 수 없다. Compose의 단일 서버 운영은 가능한 배포 방식이지만 다중 서버 장애 전환을 제공하지 않는다. [Docker Compose 운영 문서](https://docs.docker.com/compose/how-tos/production/)

인터넷에는 443만 서비스하고 80은 HTTPS 전환에만 쓴다. SSH는 관리 목적의 제한된 접근만 허용한다. API 내부 포트·작업자·DB 5432를 전체 인터넷에 열지 않는다. 관리형 DB는 가능한 사설 연결을 쓰고, 여의치 않으면 VM 출처만 허용하며 인증서 검증을 포함한 TLS를 사용한다.

보조 IP 속도 제한에서도 클라이언트가 보낸 `X-Forwarded-For`·`Forwarded`를 그대로 신뢰하지 않는다. 실제 연결 출처가 등록된 역방향 프록시일 때만 지정된 전달 헤더를 사용하고, 경계 프록시는 외부에서 온 같은 헤더를 제거·덮어쓴다. FastAPI의 forwarded IP 신뢰 설정을 실제 프록시 출처로 제한하고 직접 API 포트 접속을 막는다. 가짜 전달 헤더로 트래픽 제한을 우회하거나 다른 출처를 오인 차단하지 않는지 시험한다. [FastAPI Behind a Proxy](https://fastapi.tiangolo.com/advanced/behind-a-proxy/)

운영 비밀은 서버의 제한된 파일 또는 배포 환경 비밀 저장소로 주입한다. Git·Dockerfile·이미지·React 환경변수에 DB 비밀번호·서명 키를 넣지 않는다. Compose secrets는 필요한 컨테이너에만 파일을 제공하므로 사용할 수 있지만 호스트 원본 파일까지 자동 암호화하는 것으로 오해하지 않는다. [Docker Compose secrets](https://docs.docker.com/compose/how-tos/use-secrets/)

배포 전용 OS 계정과 DB 계정을 사용한다. API·작업자 계정은 superuser·스키마 owner가 아니며 필요한 데이터·큐 권한만 갖는다. 스키마 migration 계정은 배포 시에만 사용한다. 키·DB 자격 노출 때는 Git에서 지우는 것에 그치지 않고 즉시 폐기·교체한다.

SSE 경로는 프록시 buffering과 캐시를 끄고 heartbeat보다 긴 연결 timeout을 둔다. heartbeat는 DB 준비 여부와 별개인 브라우저 연결 신호다. 노트북 절전·브라우저 백그라운드·학교 네트워크에서 실제 테스트한다. 연결 실패 때 프론트는 현재 화면을 오래된 상태라고 표시하고 재연결 후 state를 다시 읽는다.

## 10. 배포·백업·장애 대응

첫 배포는 수동 절차로 시작하고, PR 검사 후 같은 이미지 버전을 배포한다. 운영 서버에서 즉석 수정하고 저장소와 다른 코드로 남기지 않는다.

1. PR에서 lint·타입·의미 있는 단위/통합 테스트와 API 계약을 확인한다.
2. 테스트용 DB에서 migration을 적용하고 되돌림·이전 버전 호환을 점검한다.
3. 현재 이미지·모델 버전·DB 백업 시각을 기록한다.
4. 짧은 유지보수 중에는 신규 접수를 중단하고 처리 중 작업을 안전하게 종료하거나 기한 복구 경로에 넘긴다.
5. 운영 migration을 한 번 적용하고 API·작업자를 배포한다.
6. 로그인·QR 교환·접수·검수·전광판·숨김을 별도 테스트 참여자로 점검한다.
7. 실패하면 이전 이미지로 되돌린다. 파괴적 DB 변경은 이미지 rollback으로 복구되지 않으므로 별도 복원 계획 없이 배포하지 않는다.

GitHub Actions를 연결할 때는 PR 코드가 운영 비밀을 받지 않게 하고 최소 token 권한을 사용한다. 외부 action 버전을 고정하고 배포 권한은 필요한 workflow에만 둔다. `.env.example`에는 이름·예시만 둔다. [GitHub Actions 보안 문서](https://docs.github.com/en/actions/reference/security/secure-use)

백업 초기 목표는 매일 암호화된 백업, VM 외부 저장, 7일 순환이다. 이 경우 DB 장애의 데이터 유실 목표 RPO는 최대 24시간이며 무손실을 약속하지 않는다. 학교 운영에서 이 유실 폭이 허용되지 않으면 구매 전에 관리형 DB의 PITR/WAL 보관 기능과 비용을 확인해 목표를 줄인다. 운영 재개 RTO 목표는 4시간이지만 복원 훈련 전에는 측정된 보장이 아니다. PostgreSQL의 dump·파일 백업·연속 보관은 서로 다른 복구 특성을 가진다. [PostgreSQL Backup and Restore](https://www.postgresql.org/docs/current/backup.html)

첫 공개 전에는 빈 테스트 DB로 실제 복원한다. 복원 후 오래된 처리 중 작업의 기한·중복 확정 방어를 확인하고, 원문 삭제 정책을 다시 적용한다. 해지된 자격이 백업에서 되살아날 수 있으므로 운영자·장치 세션과 미사용 pairing code를 폐기하고 운영자 재로그인·장치 재등록을 거친다. 학생 세션은 단순 복원에서는 원래 만료를 검사해 유지하되 보안 사고라면 전체 해지한다. 복구 시점 이후 작성 횟수·제재도 유실될 수 있으므로 그날 상태를 운영자가 점검한 뒤 접수를 재개한다. 최근 백업 성공 시각과 복원 소요 시간을 기록한다. DB 파일이 VM에 남아 있다는 것은 백업 성공이 아니다.

| 장애 | 운영 행동 |
|---|---|
| DB 연결 실패 | 신규 접수 실패 처리, 503 안내. 로컬 임시 저장으로 작성 제한을 우회하지 않음 |
| 모델 미준비·오류 | 신규 접수 일시중단, 이미 받은 작업은 기한·재시도 정책으로 종료. 미검수 글 게시 금지 |
| 추론 hang | supervisor가 작업자 프로세스를 종료·재시작. API의 기한 정리 작업이 독립적으로 슬롯 반환 |
| 검수 작업 중복 실행 | 제출 상태·처리 번호 검사로 한 번만 확정. 큐의 재시도 횟수와 사용자 위반 횟수 분리 |
| 전광판 연결 끊김 | 표시 진행 중단 정책 적용, 복귀 때 DB snapshot 재조회 |
| 부적절 글 노출 | 운영자가 즉시 숨김·송출 중단, 감사 기록, 필터·모델 평가셋에 별도 검토 후 반영 |
| QR 키·장치 비밀 노출 | 해당 키·자격 해지, 장치 재등록, 접근 로그 점검. 과거 기록 삭제로 끝내지 않음 |
| VM 장애 | 이미지·설정·외부 DB/백업으로 새 VM 구성. 전광판 노트북을 임시 공개 DB 서버로 만들지 않음 |

추론 감시는 컨테이너의 부모 프로세스가 별도 프로세스 그룹의 작업자 한 개를 관리하는 방식이다. 모델 시작 READY 상한은 180초다. 최대 60초 실행 임대는 claim부터 최종화까지 공유하고 부모의 작업 예산은 DB `processing_lease_until`까지 남은 시간이다. START/ACK에서 새 60초를 주지 않는다. 부모는 작업 ID·run token이 있는 START/ACK/DONE을 전용 IPC에서 확인한다. 기한 초과 시 TERM → 최대 5초 → KILL → 종료 수거 후 부모도 오류 종료하고 restart policy로 재시작한다. `unhealthy` 표시만으로 Docker가 자동 재시작한다고 가정하지 않는다. API의 제출 기한 정리와 이 실행 감시는 독립적이다. 구체 계약과 검증은 [AI 계약](ai-contract.md)을 따른다.

## 11. 관측과 출시 확인

관측값은 학생 원문 없이 집계한다. 요청 지연·오류율, DB pool 대기, 검수 대기 수·최고 대기 시간, 판정 시간, 모델 준비 상태, 기한 초과 수, 남은 예약 수, 장치 마지막 heartbeat, 백업 마지막 성공을 본다. 개인 ID·원문을 metric label로 넣지 않는다.

가동 목표는 실제 운영 시간과 예산을 합의한 뒤 정한다. 초기에는 숫자 가용성을 보장하기보다 다음 사실을 확인할 수 있어야 한다.

- API process 생존과 DB 준비 상태를 구분한다.
- 모델 process 생존과 모델 로드·추론 가능 상태를 구분한다.
- 검수 supervisor가 모델 READY를 확인한 뒤 독립된 DB readiness 임대 행을 5초마다 갱신하고 임대는 15초 유효하다. API는 유효한 임대만 신뢰한다. 프로세스가 존재하거나 queue worker가 polling 중이라는 이유로 모델 준비 상태를 추정하지 않는다.
- DB·모델이 준비되지 않으면 접수 성공을 반환하지 않는다.
- 작업 기한이 120초 또는 자정에 도달하면 API 기한 정리가 진행 중 예약을 회수한다.
- 표시·기한 정리 루프의 마지막 실행 시각을 별도로 관측한다.
- 인증·권한·기한·중복 실행 테스트를 CI에서 반복한다.

첫 교내 시험 전 필수 검증은 다음과 같다.

| 시험 | 통과 조건 |
|---|---|
| 다른 학생의 제출 ID 조회 | 일관된 404, 원문·상태 노출 없음 |
| 학생·장치 쿠키로 운영자 동작 호출 | 거부, 아무 상태도 바뀌지 않음 |
| Origin·CSRF·content type 변조 | 신규 상태 변경 거부 |
