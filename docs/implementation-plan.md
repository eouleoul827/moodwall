# 역할과 구현 순서

일반 백엔드는 한 명이 맡고 AI 담당은 모델과 추론 모듈을 책임집니다. 첫 목표는 더미 검수로 QR 입장부터 전광판 표시까지 연결하는 것입니다. 모델 학습 완료를 기다리지 않고 화면과 서버를 병행 개발합니다.

## 담당 결과물

| 담당 | 책임 | 납품 기준 |
| --- | --- | --- |
| 일반 백엔드 | 세션, QR, DB, 접수, 제한, 작업 큐, 표시 상태, 운영자, 배포 | API 계약, 트랜잭션 테스트, 실행과 복구 절차 |
| AI | 공개 적합성·감정의 라벨과 데이터, 학습, 평가, 추론 어댑터, 모델 아티팩트 | 두 판정이 분리된 실행 모듈, fake 어댑터, 평가셋 결과, 버전·오류·메모리 측정 |
| 프론트 작성 | QR 교환, 작성, emojiId 선택, 제한과 결과 안내 | API 예시 기반 화면, 재전송에 같은 요청 키 유지 |
| 프론트 전광판 | 기기 등록 화면, QR, 일반 말풍선·1시간 뒤 당일 투명 전환, 애니메이션, 운영 중단·재개 | 서버 DB 1시간 보관과 로컬 자정 보관 분리, 당일 캐시·명시적 숨김·기기 세대·재연결 |

AI 담당은 모델 파일만 전달하지 않습니다. [AI 계약](ai-contract.md)에 따라 Python에서 불러 실행할 수 있는 코드, 필요한 환경, 예문, 실패 동작을 함께 전달합니다. 데이터와 가중치는 Git에 직접 넣지 않습니다.

바로 전달할 문구와 AI 작업별 완료 조건은 [AI 담당 요청서](ai-team-request.md)에 있습니다. AI 담당은 공개 적합성 판정·감정 분류·추론 모듈·평가를 맡습니다. 일반 백엔드는 규칙 기반 욕설 필터, 작업자·감시 프로세스, 게시·제재·DB·배포를 구현합니다. 공통 입출력 스키마는 AI 담당이 코드로 제공하고 일반 백엔드가 검토하여 함께 고정합니다. AI가 애니메이션 코드를 생성하지 않으며, 감정과 animationId의 매핑은 백엔드, 실제 효과 구현은 전광판 프론트가 담당합니다.

구현 시작 전에 프론트와 [HTTP·클래스 계약](backend-contracts.md)의 공통 오류 Problem, 같은 요청 키 재전송, 목록·snapshot 규칙을 확인합니다. 실제 CI job과 배포·성능·복원 수락 기준은 [운영 실행 기준](delivery-and-operations.md)에 있습니다.

일반 백엔드의 구체적 클래스·API·PR 순서와 먼저 증명할 세 기술 검증은 [담당자 구현 계획](backend-owner-plan.md)에 있습니다. 최초 구현에서는 Linux 개발 환경·psycopg 3·Alembic revision·같은 DB 연결의 job 등록을 고정하고, 작업 hang 회수를 모델 연결 전에 시험합니다. 전광판 프론트와는 [실제 노트북의 동기화·절전 복구](display-laptop.md)를 함께 확인합니다. [전체 분기표](backend-completeness-tree.md)는 기능별 경계와 API의 연결을 확인하는 기준입니다. 첫 제품은 챗봇 모델·UI·실제 전환 연동을 제외하며 예약 mode API만 합성 시험합니다.

## 저장소 협업

Git은 각 컴퓨터의 변경 이력을 관리하는 도구이고, GitHub는 팀이 그 이력을 공유하고 검토하는 곳입니다. 친구 추가 대신 저장소 소유자가 `eouleoul827/moodwall`의 **Settings → Collaborators → Add people**에서 팀원 3명의 GitHub 계정을 초대하고, 팀원이 초대를 수락합니다. 계정·비밀번호를 공유하지 않습니다. [GitHub 협업자 초대](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/repository-access-and-collaboration/inviting-collaborators-to-a-personal-repository)

팀원은 Git 설치 후 원하는 작업 폴더에서 한 번만 아래 명령으로 복제합니다. 이미 이 저장소를 clone한 사람은 다시 실행하지 않습니다.

```powershell
git clone https://github.com/eouleoul827/moodwall.git
Set-Location moodwall
```

모두 같은 저장소를 clone하고 본인 컴퓨터에서 개발합니다. `main`은 함께 실행 가능한 통합본으로 관리합니다. 처음에는 아래 폴더만 만들고 실제 코드가 생길 때 추가합니다.

```text
frontend/                 React 작성 화면과 전광판
backend/app/              FastAPI와 업무 로직
backend/app/migrations/   앱 schema revision, 배포 시 한 번 적용
backend/inference/        AI 담당의 추론 어댑터
training/                 학습 코드와 재현 설정
docs/                     설계와 API 계약
infra/                    실행과 배포 설정
```

각 Issue에 담당자 한 명, 완료 조건, 확인 방법을 적습니다. `feat/12-admission`처럼 기능 브랜치를 만들고 1~2일 안에 검토할 수 있는 크기로 PR을 올립니다. 다른 팀원이 동작과 변경을 확인한 뒤 Squash merge합니다. API 변경 PR은 관련 프론트 담당자도 확인합니다. 모든 리뷰를 일반 백엔드 한 명에게 몰지 않습니다.

```powershell
# 작업 중인 변경이 없는 상태에서 새 기능 시작
git switch main
git pull --ff-only origin main
git switch -c feat/12-admission

# 코드 수정 및 실행 확인 후, 실제 변경한 파일을 지정
git status
git diff
git add backend/app/admission.py
git diff --staged
git commit -m "feat: QR 입장 처리"
git push -u origin feat/12-admission
```

파일 경로는 구현 시 생기는 예시입니다. GitHub에서 PR을 열고 변경 동작, 확인 결과, 관련 Issue를 적습니다. 같은 PR 수정은 같은 브랜치에 commit과 push합니다. 합쳐진 다음 새 작업은 최신 main에서 시작합니다. 다른 main 변경을 내 브랜치에 반영할 때는 내 작업을 먼저 commit한 뒤 `git fetch origin`, `git merge origin/main`을 실행합니다. 충돌은 관련 담당자와 내용을 확인하고 해결합니다.

`.env`, 비밀키, 실제 학생 원문, DB 덤프, 가중치를 커밋하지 않습니다. 환경변수 이름은 `.env.example`, 의존성은 각 생태계의 lock 파일로 공유합니다. 강제 push와 공유 기록 삭제를 기본 흐름에 넣지 않습니다.

GitHub에서 제공되는 요금제라면 main의 PR, 승인 1명, 검사 통과를 강제합니다. 비공개 저장소의 보호 기능은 계정과 조직 요금제를 확인합니다. [GitHub Flow](https://docs.github.com/en/get-started/using-github/github-flow), [브랜치 보호](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)

## 프론트와 함께 확인할 계약

- 202는 검수 접수입니다. APPROVED로 확정되면 FLOATING 공개 대상이며 실제 전광판 수신·시청과는 구분합니다.
- 같은 의도의 재전송에는 같은 Idempotency-Key를 사용합니다. 내용 수정과 새 제출에만 새 키를 만듭니다.
- 검수 중에는 추가 제출을 막고 최종 결과에서 입력을 다시 활성화합니다.
- 요청 실패로 결과를 모를 때 새 키를 자동 발급하지 않습니다. 기존 키로 재조회 또는 재전송합니다.
- 입장권 만료 시 작성 내용은 남기고 새 QR을 요구합니다. 자정에 아직 유효한 QR 입장권까지 자동 폐기하지 않으며, 작성 한도도 최근 60분으로 유지됩니다. 전날 검수 기한은 원래 날짜에서 끝나고 같은 키 재시도는 원래 결과를 반환합니다.
- 전광판은 서버 상태를 렌더링하며 브라우저의 애니메이션 종료만으로 다음 글을 선택하지 않습니다.

## 배포 책임

초기에는 백엔드 담당자가 선택한 커밋을 검증하고 수동 배포합니다. 이후 PR 검사를 통과한 main 커밋에 자동 배포를 연결합니다. GitHub 업로드와 실제 서비스 배포는 별개입니다. 개발 DB와 운영 DB는 분리합니다.

API와 worker는 같은 버전의 이미지로 만들고 시작 명령만 구분합니다. migration은 배포 작업 한 곳에서 실행합니다. 비밀값은 서버 설정으로 주입합니다. 단일 VM 구성은 해당 VM 장애 시 전체 API가 중단될 수 있으므로 [운영 절차](security-and-operations.md)에 백업과 복구를 둡니다.
