# 전광판 오류 비노출과 기존 동작 보존 설계

기준일: 2026-11-05. 공개 오류 비노출·직원 설정 분리·재생과 캐시 복구를 구현했다. 최신 적용 범위와 남은 현장 검증은 [구현 기록](display-recovery-implementation.md)을 따른다. 공개 전광판에는 장애 안내·등록 폼·재시도 버튼을 띄우지 않는다. 오류가 발생하면 허용된 콘텐츠와 기존 디자인의 기본 배경을 표시하고, 직원에게는 별도 설정 화면과 운영자 진단으로 알린다. 오류를 숨기기 위해 게시 성공·재생 완료·접속 정상 상태를 만들어 내지는 않는다.

이 설계는 [15초 재생 계약](playback-design.md)에 추가한다. 아래 회귀 검증과 실제 노트북 검증을 구분해 적용한다.

## 유지할 동작

| 대상 | 보존할 계약 |
| --- | --- |
| 접수 | 현재 30자, 최근 60분 3회, 10초 간격, 검수 중 1개와 기존 인증·QR 정책 유지 |
| 검수 | 공개 허용 판단과 감정·테마 준비를 마친 글만 READY. AI 장애를 공개 허용으로 바꾸지 않음 |
| 순서 | DB에 준비 완료 순번을 확정한 순서. 느린 글 때문에 아직 준비되지 않은 글을 먼저 표시하지 않음 |
| 재생 | 한 번에 한 글. 정상 재생은 첫 프레임 이후 최소 15,000ms, 새 글 도착 때문에 중간 교체하지 않음 |
| 완료 | 서버의 complete 확인 전 다음 글을 시작하거나 완료된 말풍선으로 확정하지 않음. 응답 유실은 기존 동일 명령으로 복구 |
| 보관 | 최초 start 승인부터 1시간 후 서버 원문 공급 종료·정리. 이미 받은 완료 말풍선은 같은 내용의 투명 말풍선으로 KST 자정까지 유지 |
| 보안 제어 | 관리자 숨김, 인증 해지, 장치 세대 변경, 재생 소유권, 온라인 허가 만료, 자정 경계를 우선 적용 |
| 직원 실행 | 기존 `/display` 주소, Windows 전용 브라우저 프로필과 장치 쿠키를 유지. 처음 등록한 뒤 매번 코드를 요구하지 않음 |
| 운영 시간 | 06:00~23:00 KST 화면 운영 조건 유지. 이번 변경으로 시간에 따른 새 접수 차단을 추가하지 않음 |
| 학생 화면 | 기존 접수 완료 카드와 필요한 오류 안내 유지. 내부 처리 단계를 새 화면으로 늘리지 않음 |

15초는 정상적으로 표시할 수 있을 때의 최소 시간이다. 관리자 숨김·인증 해지·권한 만료·화면 닫힘이 발생하면 15초 이전이라도 중단한다. 이때 완료로 기록하지 않고 기존 중단 복구 정책을 따른다. 화면 전원이나 케이블 분리는 브라우저의 재생 보고만으로 확인할 수 없다.

## 공개 화면과 직원 화면

| 경로 | 역할과 접근 |
| --- | --- |
| `/display` | 공개 송출 전용. 미등록·통신 실패·인증 만료도 기본 배경. 자동으로 설정 페이지로 이동하지 않음 |
| `/display/setup` | 새로 추가할 직원의 명시적 설정 진입점. 기존 페어링·재연결·전체 화면 안내·당일 말풍선 관리 링크를 이곳으로 옮김 |
| `/operator` | 기존 운영자 인증 유지. 숨김·중단·접수 제어와 진단 확인. 공개 전광판에서 자동으로 열지 않음 |

설정 경로를 아는 것만으로 운영 권한을 주지 않는다. 기존 일회용 페어링 코드와 장치 쿠키·Origin·CSRF 검증, 운영자 로그인을 그대로 사용한다. `/display/setup`은 재생 claim·heartbeat를 실행하지 않아 송출 탭의 소유권을 빼앗지 않는다. 설정 완료 후 같은 프로필에서 `/display`를 연다.

이미 공개 탭이 열려 있다면 직원 설정 완료 신호나 화면 복귀를 계기로 GET 세션 재검증을 한 번 수행한다. 창 사이의 신호에는 코드·쿠키·CSRF를 넣지 않고 재조회 계기로만 쓴다. 같은 장치 자격의 단순 조회 성공은 진행 중인 runtime을 재생성하지 않는다. 실제 재등록·세대 변경일 때만 옛 runtime을 정리하고 새 runtime 하나를 시작한다. 설정 완료·아이콘 재실행으로 운영자의 PAUSED나 접수 중단을 해제하지 않는다.

원문이 서버에서 삭제된 투명 말풍선도 숨김 관리가 가능해야 한다. 기존 공개 화면의 로컬 말풍선 목록을 직원 설정 화면으로 옮기고, 현재 장치 인증·날짜·세대·캐시 초기화 값과 서버 숨김 목록을 확인한 뒤 목록을 읽는다. 숨김 링크에는 UUID만 넣고 최종 숨김은 기존 운영자 인증 API에서 실행한다. 설정 진입 시 당일 캐시를 비우지 않는다.

직원용 목록은 공개 송출용 `cache.view()`와 구분한다. heartbeat를 보내지 않는 설정 화면에서도 인증·날짜·세대·숨김 검증을 마치면 관리할 수 있어야 한다. 일반 목록 조회는 저장소 읽기 전용으로 두고, 송출 탭이 정상 캐시 쓰기를 담당한다. 조회마다 저장하는 기존 `synchronize()`를 설정 탭에서 그대로 호출해 오래된 목록으로 캐시를 덮어쓰지 않는다. 인증 해제·명시적 숨김·reset의 삭제는 별도 제어 경로다.

React 라우트와 `backend/app/frontend.py`의 명시적 페이지 허용 목록에 `/display/setup`을 함께 추가한다. 없는 API 경로를 HTML로 응답하는 범용 SPA 라우트는 추가하지 않는다. 기존 런처의 송출 주소 허용 규칙은 `/display`로 유지하고, 별도 직원 설정 동작에서만 검증된 동일 origin에 고정된 `/display/setup` 경로를 붙인다. 임의 URL·query·fragment를 허용하지 않는다.

## 장애별 화면과 처리

| 상황 | 공개 화면 | 내부 처리와 복구 |
| --- | --- | --- |
| 시작 중 또는 세션 조회 5xx·timeout | 기본 배경·로고 | 기존 5→10→20→30초 직렬 재시도 유지. 중첩 요청 없음 |
| 미등록·401·403 | 기본 배경, 본문·QR 없음 | 기존 인증 초기화와 요청 취소. 공개 등록 폼 없음. 자동 재등록·인증 실패 무한 재시도 금지 |
| QR 발급·이미지 변환 실패 | QR 자리를 같은 크기의 장식으로 유지 | 유효한 기존 QR은 자체 만료 전까지 사용 가능. 만료되면 QR과 해당 스캔 안내를 함께 감춤 |
| SSE만 끊김 | 정상 화면 | 기존 HTTP 동기화가 성공하면 계속 재생. SSE 오류만으로 전체 화면 중단하지 않음 |
| API 일시 단절 | 현재 허가 범위의 글 또는 기본 배경 | 이미 승인된 재생은 자체 허가 기한 안에서만 유지. 기존 캐시 동기화 실패의 숨김 규칙을 완화하지 않음 |
| 재생 허가 만료·다른 창 소유 | 기본 배경 | 본문 숨김, 소유권 탈취 금지. 서버 상태 확인 뒤 기존 소유권 정책으로 복구 |
| 글꼴·테마 준비 실패 | 기존 벽 또는 기본 배경 | 해당 글을 표시하지 않고 기존 중단 절차. 실패한 prepare를 성공으로 바꾸지 않음 |
| complete 응답 유실 | 기존 캐시 표시가 허용되면 기존 벽, 아니면 기본 배경 | UNKNOWN 유지, 같은 명령 확인. 새 글 선점·임의 DONE 금지 |
| 관리자 숨김·일시 중단 | 승인된 제어에 맞춰 글을 내리고 기본 배경 | 숨김 표식과 서버 attempt 상태 적용. 진단 전송을 기다리지 않고 제어 실행 |
| React 렌더 오류·애니메이션 루프 오류 | 글 없는 기본 배경 | 런타임 종료·비동기 작업 취소·중단 보고 시도. 안전한 자동 복구 범위 밖이면 직원 조치 |
| localStorage 사용 실패 | 메모리의 허용된 당일 말풍선 | 메모리 재생 유지, 영속 보관 실패는 직원 진단. 저장 실패를 인증 해지로 취급하지 않음 |
| 자정·절전 후 날짜 변경 | 기본 배경에서 당일 상태 재확인 | 이전 날 캐시와 대기 정책 적용. 전날 내용이 한 프레임 먼저 나타나지 않음 |

기본 배경은 정상적인 빈 무드월과 같은 색·로고·장식으로 만든다. 오류 문구, 로딩 스피너, 등록 코드, 복구 버튼, 개발 오류 코드와 alert를 넣지 않는다. 공개 오류를 CSS로만 숨긴 채 접근성 트리·title·aria-live에 남기지도 않는다. 정상 게시글의 접근성 정보는 유지한다.

QR이 없을 때는 일반 벽과 전체 화면 게시글 양쪽의 스캔 안내를 함께 처리한다. 기본 배경에서 임의의 학생 글이나 감정 통계를 만들어 내지 않는다. 상태를 모르는 상황을 “오늘 0개”로 단정하지 않고 숫자·감정 비율 대신 기존 브랜드 장식을 사용한다. 유효한 동기화 결과가 실제 0개인 경우에는 기존 빈 화면을 유지한다.

기본 배경으로 전체 전환한 상태에는 QR도 표시하지 않는다. 정상 벽에서 QR을 노출하려면 유효한 세션·현재 운영 모드·온라인 허가와 QR 자체 만료를 모두 확인한다. QR 발급 실패만 발생했다면 기존 재생 엔진은 유지한다. 이 화면 판단은 서버의 접수 정책을 변경하지 않는다.

## 코드 책임과 변경 경계

### 공개 렌더와 제어 처리 분리

`DisplayApp.jsx`의 `onProblem`과 `observedFetch`에는 인증 해제 제어가 섞여 있다. 이 콜백 자체를 제거하지 않는다. 인증·소유권·중단 처리 후 공개 화면은 허용된 view만 받고, 진단은 별도 콜백으로 전달한다.

구현 책임은 다음처럼 나눈다. 아래 이름 중 새 이름은 제안 인터페이스이며 현재 존재하는 API를 뜻하지 않는다.

| 파일 또는 구성요소 | 책임 |
| --- | --- |
| `frontend/src/App.jsx` | `/display` 전용 ErrorBoundary와 Suspense 기본 배경. 학생·운영자의 기존 오류 UI 유지 |
| `DisplayApp.jsx`와 새 `DisplaySetupApp.jsx` | 공개 렌더와 직원 폼 분리. 기존 세션·페어링 복구 함수는 공유하여 응답 유실·CSRF 갱신 동작 보존 |
| 새 `DisplayBackdrop` | 서버·외부 글꼴·QR·학생 본문에 의존하지 않는 배경. fallback 자체가 다시 실패할 가능성을 줄임 |
| `clients/display/playback-browser.mjs` | 제어 콜백 유지, 반환된 INTERRUPTED·UNKNOWN과 비동기 루프 실패를 진단에 전달 |
| `playback-controller.mjs` | 기존 start·first-frame·complete·lease 계약 유지. 관측한 서버 attempt의 종료·중단 상태 즉시 반영 |
| `playback-bubble-cache.mjs` | 일시 단절 시 숨김과 실제 삭제 구분. 완료 ACK 이후 캐시 저장과 snapshot 병합의 경쟁 방어 |
| `backend/app/frontend.py` | 새 직원 페이지 허용. 기존 API 404·CSP·캐시 정책 유지 |
| Windows 런처 | 기존 프로필·창 재사용·mutex 유지. 공개 실행과 직원 진단의 화면 출력을 분리 |

내부 진단 상태는 세션·QR·재생·캐시별로 구분한다. QR 요청 하나가 성공했다고 재생 오류까지 모두 해결된 것으로 지우지 않는다. 복구 판정은 실패했던 동작이 다시 성공했을 때 갱신한다. 기존 서버의 접수 상태 enum에 화면 상태를 덧붙이지 않는다.

연결 복구는 세션과 현재 서버 상태를 다시 확인하고, 장치 세대·재생 epoch·날짜·숨김 표식을 적용한 뒤 허용된 콘텐츠만 그린다. 지연된 옛 응답은 현재 세션을 부활시키거나 숨긴 글을 되살릴 수 없다. `navigator.onLine`은 재시도를 깨우는 신호로만 사용한다. 이 값만으로 서버에 접속됐다고 판정할 수는 없다. [MDN onLine](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/onLine)

### 렌더 오류와 자동 복구

공개 전용 ErrorBoundary는 lazy 화면 로드 실패와 React 렌더 예외를 기본 배경으로 전환한다. fallback은 실패한 DisplayApp 모듈보다 먼저 로드되는 작은 구성요소로 둔다. 최초 HTML의 root에도 같은 색과 로고의 정적 기본 화면을 두어 JS 로딩 도중의 빈 화면을 줄인다. 기존 CSP를 약화시키는 inline JavaScript는 추가하지 않는다.

Promise·이벤트·requestAnimationFrame 예외는 해당 실행 지점에서 처리해야 한다. ErrorBoundary는 일반 이벤트 핸들러나 비동기 콜백 오류를 모두 잡지 않는다. `draw`, `loop`, `prepare`, QR 변환 각각에 종료·취소 경로를 둔다. [React ErrorBoundary](https://react.dev/reference/react/Component#catching-rendering-errors-with-an-error-boundary)

네트워크 오류는 기존 재시도 루프를 사용하며 페이지 전체를 새로고침하지 않는다. 렌더러가 무너진 경우에는 즉시 본문을 숨기고 runtime을 정리한 뒤 기본 배경을 유지한다. 초기 구현에서는 이 경우 직원의 명시적 복구를 사용한다. 자동 remount·새로고침을 추가하려면 완료 결과가 불확실한 기존 attempt와 단일 소유권을 먼저 복구하는 별도 검증이 필요하다. 런타임의 cleanup은 중복 호출에도 안전해야 하고, 실패한 진단 전송 때문에 종료가 멈추지 않아야 한다.

### 기존 검토에서 발견한 재생 회귀 위험 보완

1. `#observe()`는 현재 재생 중인 동일 attempt가 서버에서도 `PLAYING`인지 확인한다. PAUSED→MOODWALL이 관측 사이에 지나가도 서버 attempt가 `INTERRUPTED`이면 즉시 숨기고 기존 복구 경로를 따른다. ID와 mode만 같다는 이유로 15초를 계속 채우지 않는다.
2. 유효한 complete ACK를 받으면 완료 카드가 snapshot에 다시 실릴 때까지 기다리지 않고 캐시에 반영한다. 이를 위한 `cache.acceptCompleted(...)`를 별도로 추가하고 기존 카드 필드 검증을 재사용한다. ACK 유실인 UNKNOWN은 대상이 아니다.
3. ACK로 캐시에 넣을 때 현재 board·날짜·장치 세대·초기화 값·revision·숨김 표식과 응답을 검사한다. attempt와 presentation이 모두 DONE일 때만 저장한다. HIDDEN·FAILED·EXPIRED·CANCELLED와 진행 상태는 제외한다. 로컬에서 이미 알려진 숨김·reset·인증 수명보다 오래된 ACK는 무시한다. ACK만으로 온라인 허가를 늘리거나 소유권을 회복시키지 않는다.
4. 초기 snapshot이 실패한 경우에도 완료 카드를 잃지 않도록, 완료 응답에 서버가 확정한 캐시 scope(board·업무 날짜·장치 세대·초기화 값·revision·서버 시각·자정)를 추가한다. 유효한 scope와 실제 수신한 완료 카드를 저장하고, 같은 scope의 이전 저장소 카드는 기존 필드 검증과 숨김 표식을 적용해 비공개 캐시로 복구할 수 있다. ACK 하나로 공개 표시 허가를 열지 않으며 최신 snapshot 검증을 기다린다. scope 비교와 기존 카드 검증을 재사용하며, 서버·OpenAPI·fixture를 함께 변경한다. 새 필드가 없는 구버전 서버는 기존 snapshot 방식으로 동작하므로 캐시 유실 보완은 새 서버와 클라이언트가 함께 배포된 뒤 완료로 판단한다.
5. 일시 단절은 캐시 보존 후 숨김, 인증 해제는 기존 clear, 자정·세대·초기화 값 변경은 기존 초기화다. 서버 원문이 없어졌다는 이유만으로 이미 받은 당일 말풍선을 삭제하지 않는다.

## 직원 진단

초기 공개 화면 변경과 함께 기존 서버 로그의 확인 방법을 유지하고, 브라우저에서만 알 수 있는 렌더·QR·캐시 실패는 별도 진단 전달을 추가한다. 화면에 오류가 안 보이는 것과 운영자가 오류를 알 수 있는 것은 각각 검증한다.

제안 계약은 `POST /api/display/diagnostics`와 운영자 인증이 필요한 `GET /api/operator/display/diagnostics`다. 장치 쿠키·Origin·CSRF를 검증하고, board와 장치 세대는 서버 인증 문맥에서 정한다. 클라이언트 보고는 참고 정보이며 완료·heartbeat·온라인 허가·접수 횟수·AI 결과를 변경하지 않는다.

전송 필드는 허용 목록의 `component`, `code`, `state`(발생 또는 복구), 버전, 집계 횟수와 발생 시각으로 한정한다. 서버 수신 시각은 따로 기록한다. 학생 원문·이름·QR URL과 ticket·쿠키·CSRF·AI 응답·임의 stack trace를 보내지 않는다. 임의 문자열을 오류 코드로 그대로 수집하지 않는다.

초기 한도는 한 번에 4KiB, 같은 종류는 60초에 한 번으로 합산, 장치당 분당 10회 이하, 브라우저 메모리 대기 최대 20개·10분이다. 오래된 진단은 버려도 업무 처리는 유지한다. 401·403이면 보고를 중단하고 재등록 성공 뒤 새 인증 문맥으로 시작한다. 429는 Retry-After를 따르고 그 밖의 일시 실패는 다음 허용 주기에만 다시 보낸다. 진단 실패에 대한 진단을 재귀적으로 생성하지 않는다.

서버는 최신 상태와 제한된 운영 로그를 보관하고 7일 보관 정책을 적용한다. 별도 원문 사본을 만드는 오류 기록 테이블은 만들지 않는다. 초기에는 외부 메시지 발송 연동을 추가하지 않고 인증된 운영자 화면에서 확인한다. 오프라인 중에는 브라우저 보고를 받을 수 없으므로 서버의 마지막 통신 시각과 “보고 미수신” 상태도 구분한다. heartbeat만으로 실제 패널 정상 출력을 표시하지 않는다.

## Windows 실행과 물리적인 화면 경계

현재 `Start-Display.ps1`은 연결 실패 등에 MessageBox를 표시한다. 숨겨진 PowerShell 실행은 이 팝업까지 숨기지 않는다. 공개 실행에서는 모달·알림창을 띄우지 않고 결과 코드를 남기며, 직원 진단 실행에서만 자세한 오류와 재시도를 제공하도록 나눈다. 로그는 제한·순환하고 인증값을 넣지 않는다.

직원 설정은 동일 전용 브라우저 프로필에서 수행한다. 다른 PC나 휴대폰으로 페어링 POST를 대신하면 전광판 프로필에 쿠키가 설치되지 않는다. 휴대폰에서는 운영자 코드 발급·진단을 확인할 수 있지만 최초 코드는 전광판 프로필에 입력해야 한다. 기본 절차는 직원 설정 완료 후 패널을 켜는 것이다. Windows 확장 모니터를 사용할 때만 설정 창과 공개 송출 창을 물리적으로 분리할 수 있다.

복제 화면에서는 노트북의 팝업·설정·OS 알림도 전광판에 보인다. 설치와 현장 운영 검증에 이 조건을 포함한다. 공개 실행 전 이미 떠 있는 정상 송출 창을 발견하면 기존 창을 재사용하고 종료·재실행하지 않는다.

같은 프로필의 첫 창을 무조건 활성화하면 직원 설정 창이 공개될 수 있다. 기본 직원 절차는 설정을 마친 창을 `/display`로 복귀시켜 송출 창 하나만 남기는 방식이다. 별도 설정 창을 유지하는 확장 모드 운영은 창 역할을 검증해 송출 창만 선택할 수 있을 때 지원한다. 잘못된 창을 임의 활성화하지 않는다. 실패한 공개 창은 직원이 명시적으로 새로고침할 수 있지만, 프로필·캐시는 보존하고 기존 서버의 미확정 attempt 복구를 따른다. 정상 창 재사용과 실패 창의 명시적 복구는 별도 동작으로 둔다.

웹앱이 실행된 뒤의 오류 비노출과, 첫 HTML조차 받지 못한 DNS·TLS·브라우저 오류는 보장 범위가 다르다. 최초 접속 실패까지 조용히 처리하려면 런처가 먼저 로컬 기본 화면을 띄우는 보완이 필요하다. 원격 페이지 로드 전환 중 실패하는 경우까지 가리는 별도 실행기 구현은 이번 React 수정만으로 충족됐다고 표시하지 않는다. 초기 배포는 실제 주소로 직원 시작 점검을 마친 뒤 패널을 켜고, 브라우저 종료·재부팅·절전은 현장 시험에서 확인한다.

## 전체 흐름의 나머지 수정 대상

앞선 흐름 검토에서 확인한 항목은 공개 오류 처리와 분리해 아래 순서로 반영한다. 동시에 진행 중인 AI·신고 기능 변경을 덮어쓰지 않고, 통합할 최종 소스 기준으로 다시 검사한다.

| 항목 | 수정 설계 | 기존 동작 보호 조건 |
| --- | --- | --- |
| 이전 v1 접수와 v2 전광판 불일치 | v2 운영에서 새 v1 접수는 업데이트 필요로 거절. 이미 접수한 요청의 동일 키 조회·재응답은 허용 | 정상 v2와 기존 영수증 복구 유지. 배포 설정별 호환 테스트 |
| 접수 성공 응답 유실 후 새로고침 | 전송 전에 UUID를 sessionStorage에 보관하고, 본인 영수증 조회 후 새 접수 여부 결정. 본문 저장 없음 | 저장 불가 시 메모리 복구 유지. 알 수 없는 결과에 새 UUID를 자동 발급하지 않음 |
| 일반 503의 접수 결과 불확실성 | 명시적 업무 거절과 기술 실패를 구분. 일반 5xx는 같은 키로 확인·재시도 | 실제 commit 이후 응답 유실을 통합 테스트. 네트워크 오류를 성공이나 확정 실패로 단정하지 않음 |
| 학생 결과 확인이 대기 기한보다 먼저 종료 | 영수증의 상태·기한 기반으로 polling, 화면 복귀 때 재조회. timeout이면 기존 완료 카드에 거짓 실패를 추가하지 않음 | 완료 카드와 기존 짧은 실패 안내 유지, terminal 이후 polling 중단 |
| Gemini 공개 허용 뒤 감정 연결 누락 | 평가된 감정 predictor를 연결하고 허용→감정→테마→READY 순서 보장 | 검수 실패를 NEUTRAL로 우회하지 않음. 감정만 불확실할 때의 중립 테마는 명시한 모델 계약에 한정 |
| 정리 작업 비활성화가 production에서 허용 | 내부 정리 루프가 꺼진 production 설정은 실패 처리. 외부 작업자 지원은 생존 확인을 함께 설계할 때 추가 | 개발·테스트 설정 유지. 지연 후 재가동 시 원문 정리와 대기 만료가 따라잡는지 확인 |
| Compose DB 재시작 | 실제 Compose 운영이면 DB 재시작 정책과 재부팅 복구 시험 추가 | 볼륨 삭제·DB 초기화 없이 회복. 관리형 DB 운영에는 별도 가용성 설정 사용 |
| 당일 캐시 기본 2000개와 프레임별 정렬 | 저장 용량과 동시 렌더 비용을 분리해 계측. 내용·phase 변경 때만 정렬 갱신 | 4개 상한 도입 금지. 오래된 말풍선을 묵시적으로 버리는 정책은 “하루 유지” 충족으로 보지 않음 |
| 신고 세션 만료 재시도 | 세션·CSRF를 한 번 갱신하고 같은 신고 UUID로 복구, 인증이 없으면 재입장 안내 | 성공을 중복 기록하지 않음. 신고 창 재진입 상태도 확인 |

캐시 상한은 기본 5000개·설정 최대 10000개로 제한하고 프레임마다 정렬하지 않는다. 17시간 동안 15초 간격의 이론상 최대 4080개에 대해 직렬화·복구·view 재사용을 synthetic 검사했다. 저장소 복구의 기존 길이 검사는 4,000,000 UTF-16 code unit이며 바이트 4MB 보장은 아니다. 복합 이모지로 실제 저장소 용량을 넘으면 메모리 재생과 직원 진단을 유지한다. 실제 노트북의 DOM·프레임 시간·발열은 별도로 측정한다. 이미 서버 원문과 로컬 저장소가 모두 지워진 카드는 복구할 수 없다.

| KST 자정·장시간 절전 복귀 | 이전 날 글·QR이 한 프레임 먼저 노출되지 않음 |
| 저장소 거절·용량 초과 | 앱 크래시와 공개 경고 없이 메모리 재생, 직원에게 저장 지속성 문제 전달 |
| React 예외·RAF 예외·폰트 실패 | 기본 배경 유지, 기존 런타임 정리. 실패한 글의 거짓 DONE 없음 |
| 진단 서버 장애·401·429·중복 보고 | 재생·접수와 분리, 대기 상한 준수, 원문·비밀값 미포함 |
| 직원 설정 | 동일 프로필 쿠키, 만료 쿠키 정리·CSRF 재조회·pair 응답 유실 복구, 송출 claim·heartbeat 간섭 없음 |
| 설정 조회와 재등록 | 같은 자격 조회는 15초 재생을 끊지 않음. 실제 세대 변경만 runtime 교체. PAUSED와 접수 중단 보존 |
| 설정의 말풍선 조회 | 원문 정리·lease 만료 뒤에도 인증된 직원 목록 확인 가능. 일반 조회로 공유 캐시를 덮어쓰지 않음 |
| 라우팅과 기존 UI | `/display/setup` 직접 접속·새로고침 성공, 없는 API는 JSON 404, 학생·운영자 오류 안내 유지 |
| Windows 실제 시작·종료 | 정상 송출 창 재사용, 공개 오류 모달 없음, 프로필 유지. 실제 HDMI 출력·절전·브라우저 종료 별도 확인 |
| 설치 갱신과 모니터 재연결 | 기존 바로가기·쿠키·캐시 유지. 직원 창을 송출 창으로 잘못 활성화하지 않음. 확장·복제 모드 각각 확인 |

1. **공개 UI와 직원 설정 분리:** API 게시 상태·DB 스키마·15초 로직을 바꾸지 않는 범위부터 적용한다. React 테스트와 페이지 제공 테스트를 함께 바꾼다. 기존 “인증 실패 시 등록 폼” 테스트의 공개 화면 기대값만 바꾸고, 등록 동작 테스트는 직원 설정 테스트로 옮긴다.
2. **재생과 캐시 복구 보완:** 서버 INTERRUPTED 관측, complete ACK 캐시 반영을 각 테스트와 함께 적용한다. `playback-controller.test.mjs`, `playback-bubble-cache.test.mjs`, React 통합 및 `backend/tests/test_playback_*.py`를 실행한다. 시각은 가짜 시계와 고정 KST 경계로 검증한다.
3. **진단과 런처 보완:** 선택적 진단 계약을 서버에 먼저 배포하고 클라이언트를 연결한다. 진단 endpoint가 없는 구버전 서버도 공개 재생은 지속해야 한다. 런처의 기존 PlanOnly·URL 검증·전용 프로필·중복 실행 테스트를 보존한다.
4. **나머지 흐름 수정:** 접수 복구·AI 감정 연결·정리 루프·신고를 각각 독립 변경으로 반영한다. 전체 프론트·클라이언트 모듈·백엔드 통합 검사 후 production build로 한 대의 실제 노트북에서 시험한다.

롤백은 DB 원문·영수증·장치 쿠키·캐시를 초기화하지 않고 배포물 단위로 한다. 신규 서버 필드는 추가 방식으로 유지한다. 공개 오류 비노출 요구가 들어가기 전 버전으로 되돌리면 오류 안내가 다시 노출될 수 있으므로, 공개 UI 분리까지 검증한 버전을 복구 기준으로 보관한다. 그 기준 버전도 불안정하면 글 없는 기본 화면을 사용하고 직원이 복구한다.

실행 코드의 검증 결과와 미완료 항목은 [구현 기록](display-recovery-implementation.md)에 구분한다. 실제 노트북·휴대폰·HDMI 시험 통과가 현장 배포의 완료 기준이다.
